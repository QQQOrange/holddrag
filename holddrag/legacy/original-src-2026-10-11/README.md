# 长按拖窗 HoldDrag

按你自己的方式拖窗口：**长按一个自定义按键，然后用鼠标左键 / 右键 / 中键做三件不同的事**。

默认配置（对齐 AltSnap 的出厂绑定，只是把修饰键换成了长按 Enter）：

| 操作 | 行为 |
| --- | --- |
| 长按 `Enter` 0.6 秒 → **左键拖动** | 移动窗口 |
| 长按 `Enter` 0.6 秒 → **右键拖动** | 调整大小（九宫格就近角/边） |
| 长按 `Enter` 0.6 秒 → **中键** | 最大化 / 还原 |
| 长按 `Enter` 0.6 秒 → **左键双击** | 最大化 / 还原 |
| 长按 `Enter` 0.6 秒 → **右键双击** | 按九宫格把窗口吸附到屏幕对应位置 |
| 把窗口拖到屏幕边缘 | 自动半屏 / 最大化（带吸附预览） |
| 长按到阈值、还没按鼠标键 | 光标底下那扇窗先亮起一圈圆角外框，告诉你"接管的是它" |

---

## 快速开始

1. 双击 `HoldDrag.exe`。**会弹一次 UAC 提权确认**（原因见下一节），点"是"。
2. 托盘区出现图标（蓝紫渐变方块 + 白色四向箭头），首次运行会有气泡提示。
3. 长按 `Enter` 约 0.6 秒不要松手 —— **这时候光标底下的窗口会立刻亮起一圈圆角外框**，说明它已经被接管了。然后按住左键拖它。
4. **双击托盘图标**打开设置窗口，改触发键、改三个鼠标键的动作、开关各项附加功能、挑外框的颜色和样式。

> 想换触发键：设置窗口里点「重新录制」→ 直接按下你想用的键。左/右/中键已被鼠标动作占用，不能当触发键；鼠标侧键（前进/后退）可以。

## 为什么需要管理员权限

早期版本里 AltSnap 官方文档也写明了同一件事：

- 全局低级键鼠钩子只有在**同级或更高权限**下，才能看到"以管理员身份运行的窗口"上的输入。若本程序不提权，你在任务管理器上按的键它根本收不到。
- 要移动/缩放提权窗口，本进程也必须是管理员。

所以**默认是开的**，但设置里可以关掉（「启动时自动申请管理员权限」）。为了不让每次开机都弹 UAC，开机自启默认走**计划任务（最高权限 + 登录时静默启动）**，而不是注册表 Run 项。

**UAC 上点了「否」会怎样？** 不会启动失败——程序**降级成普通权限继续跑**，功能照常，只是拖不动任务管理器这类提权窗口。随后弹一次询问：

- 点**确定** → 立刻重启软件并以管理员身份打开
- 点**取消** → 就这么用着，不再打扰

不想再看到这个提示，就把「没有管理员权限时提示我」关掉。

如果你只是临时想要不提权运行：

```
HoldDrag.exe --no-elevate
```

代价是提权窗口既拖不动也感知不到按键。

## 触发键的两个关键行为（务必了解）

本程序的触发键**不是普通修饰键**，而是"长按触发"，这样才能用 Enter 这种日常高频按键：

**1. 短按 = 原样透传**
按下瞬间程序就把这次按键吞掉并开始计时。如果在你设定的阈值内松手，程序会用 `SendInput` 合成一次完整的"按下 + 抬起"补发出去。所以**正常打字、回车换行、回车提交、回车确认都不受影响**（只有极微小的延迟）。

**2. 超过阈值 = 进入激活态**
此时不再补发任何按键，你按鼠标左键/右键/中键就会触发对应的窗口动作。松开触发键即退出激活态。

**必须知道的代价：** 要区分"长按"和"连发"，就必须吞掉键盘的自动重复事件。因此**按住 Enter 不放连续换行会被压成一次**。这是原理上的取舍，无法两头兼顾。

**可选：** 设置里可以关掉「需要长按触发」。关闭后这个键就变成纯修饰键——**按住立刻生效，但短按也不再发出原按键**（它彻底被本程序占用）。

### 按住触发键做完一次动作之后，外框会继续留着

用户明确提过的需求：**长按 Enter 激活 → 用左键或右键做一件事（最大化、居中、九宫格吸附、拖动…）→ 外框必须还在**，而不是消失。

这里原先漏了一条路径。拖动类动作（左键拖动、右键缩放）在 `Begin` / `End` 里自带"收起环形框 → 换分层框 → 重新亮框"的完整流程，所以它们本来就是对的；但**非拖动**的一次性动作走的是另一条路：

- 中键 / 任意键绑定成"最大化 / 最小化 / 居中 / 置顶 / 关闭"等
- 左键双击（最大化 / 还原）
- 右键双击（九宫格吸附）

这几条路径原先只做了一件事：把这个鼠标事件吞掉，然后返回。**没人去把外框重新亮回来**，于是你看到的就是"按了动作、外框没了"。松开鼠标之后光标不动，悬停刷新逻辑也不会被触发，外框就一直隐着——看起来就像功能坏了。

修法是在这几条路径后面补一次"把框重新亮回光标底下那扇窗"（`Coordinator.RefreshHoverAfterAction`），并且**强制让悬停缓存失效**：因为这类动作往往刚刚改过窗口矩形（最大化就是典型），沿用旧的"还是同一扇窗"缓存会把框留在旧位置。

> 自检 `T33` 专门守这条：中键做一次性动作、双击左键最大化，两条路径都断言外框仍然可见，直到松开触发键才消失。

### 设置窗口可以自由拉大拉小了

原先窗口是 `FixedSingle` + 禁止最大化，尺寸被钉死。现在：

- 边框可缩放、可最大化 / 最小化；
- 六个分组和底部按钮都做了**锚定**——横着拉宽，控件跟着一起变宽（否则"能拉但只多出一片空白"，等于没拉）；右列控件锚定右边，不与左列挤在一起；
- 内容高于窗口时纵向自动出滚动条，所以你也可以把它拉矮；
- 窗口尺寸会**记住**，下次打开还是你拉的那个大小（点"取消"不会留下任何痕迹，包括尺寸）；
- 手改配置文件把尺寸改成离谱数字也不会让窗口变成一个点不到按钮的怪形状，会被拉回安全区间。

### 主题为什么"改了没生效" / 拖动残影 / 抖动

#### 改了颜色样式，保存后看不出变化

外框是**分层窗口**：像素不是靠 `WM_PAINT` 画的，而是靠 `UpdateLayeredWindow` 一次性提交给合成器。改外观的旧写法只做了"重建位图"这一步，**没有接着调 `UpdateLayeredWindow`**——于是新外观静静地躺在内存里，要等到下一次 `SetRect`（也就是鼠标移开、光标换到另一扇窗）才会真的画到屏幕上。用户看到的就是"主题根本没用"。

修法：外观变更走一条独立消息（`WM_RETHEME`）回到创建浮层的那个线程，**重画 + 立刻重推像素**，并且重推时沿用上次落地的位置（改外观不该让外框自己跑位）。

> 自检 `T35` 直接 `GetDC(NULL) + GetPixel` 读屏幕像素来断言：换成朱红之后，描边位置的颜色必须立刻接近朱红而不是薄荷青。这是唯一能证明"真的画到屏幕上了"的办法。

#### 残影是怎么来的

你之前看到的"拖过之后留下一串半透明影子"，不是显卡问题，而是**实现方式的问题**。旧版用的是最直觉的做法：一个 `Form`，设 `Opacity = 0.x`，拖动时不断 `SetBounds()` 改位置再 `Refresh()`。它有三个独立的毛病，每一个都会产生残影：

**1. 移动和重画是两个动作，中间状态被你看见了。**
`SetBounds()` 把窗口搬到新位置，这一步是**立刻生效**的；但旧位置那块屏幕要在下一个 `WM_ERASEBKGND + WM_PAINT` 才被擦掉。在这两件事之间，屏幕上同时存在"新位置的窗口"和"还没擦掉的旧位置内容"。每次 `WM_MOUSEMOVE` 都留下这么一帧，鼠标一秒动几百次，就叠成一串影子。`Opacity` 让窗口变半透明之后更糟——透过它能直接看见底下的窗口，旧位置的残留就更加明显。

**2. 没有节流，消息队列被灌爆。**
鼠标每秒产生几百个移动事件，旧版每个都直接转成一个 `SetWindowPos`。目标窗口因此每秒收到几百次 `WM_WINDOWPOSCHANGING → WM_MOVE/WM_SIZE → WM_PAINT`。它处理不过来就开始丢帧、开始积压，**越拖越卡**指的就是这个积压过程。卡了之后积压更严重，旧位置擦得更慢，残影也就更明显——这解释了为什么"多滑几下"之后会明显恶化。

**3. WinForms 的 `Opacity` 走的是分层窗口（layered window）的慢路径。**
每帧都要重新合成一张带 alpha 的位图。这条路径本身就不适合每帧更新。

**现在怎么做的：**

| 问题 | 现在的实现 |
| --- | --- |
| 外框与预览 | 都用 `UpdateLayeredWindow`，**位置、尺寸、像素一次性提交**。系统不会先看到"在新位置"再看到"新内容"，两者是原子的，中间不存在可被观察到的状态。 |
| 圆角为什么是平滑的弧 | 在 32bpp 位图上用 GDI+ 的 `SmoothingMode.AntiAlias` 描边。中途走过一段弯路：曾用 `CreateRoundRectRgn` 抠"圆环" + `SetWindowRgn`，虽然也不留残影，但 **GDI 区域是没有抗锯齿的**，圆角在屏幕上就是一级一级的锯齿——你看到的"四个角又直又尖"正是这个。 |
| 节流 | 每次 `SetWindowPos` 之后按**显示器刷新率**睡一小段（自动模式下实测你的屏幕是多少 Hz 就按多少 Hz 走）。同一帧内的多次鼠标移动会被合并成一次窗口移动，消息队列不再被灌爆。 |
| 卡顿 | 提前景（`ForceForeground` / `AttachThreadInput`）和枚举窗口（`EnumWindows`）这些重活全部从钩子线程挪到后台工作线程。钩子线程只做判断和投递，立刻返回。 |
| 高频屏 | 启动时调 `timeBeginPeriod(1)`。Windows 默认定时器精度是 15.6 ms，不抬上去的话 `Thread.Sleep(3)` 实际睡 15 ms，144Hz 屏的节流会退化成 60Hz 的效果。 |
| 每帧的 GDI 开销 | 位图、GDI 位图句柄、内存 DC 三件套按尺寸缓存住，只在尺寸变化时重建。一次拖动的稳态是**零 GDI 分配、零托管分配**。 |

> 顺带一提：**被接管的窗口本身不再被改透明度了**（那本来是 AltSnap 的视觉方案，也是残影的最大来源）。现在窗口原样不动，只是外面套一圈圆角边框告诉你"它已经被接管了"。

### 外框为什么不会用完之后还留在屏幕上

这个 bug 修过一次，值得单独记一笔，因为它的成因很不直观。

`Step()`（运行在工作线程）的收尾是：先校验"会话还有效"→ 调 `SetWindowPos` → 显示外框。问题出在**中间那一步**：`SetWindowPos` 在目标窗口正忙时会阻塞几十毫秒甚至更久，而这段时间里用户已经松开鼠标，钩子线程走完了 `End()` → 收尾 → 把外框隐藏了。等工作线程从 `SetWindowPos` 里出来，它手里那份"会话仍有效"的判定早已过期，却还是照着它把外框又画了一次——**之后再没有任何人会去关掉它**。

修法是加一道闸（`DragEngine.TryShowFrame`）：**判定与投递必须在同一把锁里完成**。只要有一瞬间是在锁外做的判定，收尾线程就能钻进这个空隙把外框关掉，而我们拿着过期结论又把它画出来。自检 `T31` 会真的拿一个过期代次去调显框入口，断言它被挡下。

### 流畅度

| 开关 | 默认 | 说明 |
| --- | --- | --- |
| 拖动刷新率 | 自动（跟随屏幕） | 自动模式按实测到的显示器刷新率节流（界面会显示当前检测到多少 Hz）。也可以改成手动指定 20–500 Hz。 |

> ⚠️ **本机实测提示**：你这台机器的安全策略把 `schtasks.exe` 列入了程序黑名单，因此"计划任务"方式会被拦截。程序会自动降级为注册表方式并弹窗告知（代价是每次登录多一个 UAC 确认）。如果你想用回静默的计划任务方式，需要在安全软件里放行 `schtasks.exe`。

## 九宫格缩放是怎么判断的

按下右键拖动时，程序按"按住点"在窗口里的位置决定缩放哪个方向。角格略大于中间格（比例可调，默认 26%）：

```
 ┌───────────────┬───────────────┬───────────────┐
 │    左上角      │      上       │    右上角      │
 ├───────────────┼───────────────┼───────────────┤
 │      左       │    中心区     │      右       │
 ├───────────────┼───────────────┼───────────────┤
 │    左下角      │      下       │    右下角      │
 └───────────────┴───────────────┴───────────────┘
```

- 命中角格 → 同时拖两条边
- 命中边格 → 只拖那一条边
- 命中中心区 → 自动选最近的那个角

**双击右键**时，同一套九宫格被映射到屏幕位置：上格 → 上半屏、左格 → 左半屏、右下角 → 右下四分之一、中心区 → 最大化。**只贴屏幕下边缘不吸附**（与 Windows 原生 Aero Snap 一致）。

## 已知限制

1. **Win11 的 Snap Layouts 布局面板不会弹出。** 因为要实现"双击左键/右键"这两个功能，就不能用系统的原生拖动循环，边缘吸附是程序自己实现的（AltSnap 同样如此）。吸附的最终落点与原生一致。
2. **按住 Enter 不会连续换行**（见上文取舍）。
3. **用 Alt / Ctrl / Win 作为触发键时**，按住期间该键的组合功能不可用（例如用 Win 作触发键时 Win+E 无效）。设置窗口会给提示。
4. **CapsLock 作为触发键**时不会切换大小写（被程序压制），这也是你要"自定义按键"的必然结果。
5. 极少数自绘界面 / 全屏游戏的窗口可能无法移动或移动异常。
6. 提权窗口只有在本程序也提权时才能操作。

### ⚠️ `app.manifest` 绝对不能是非法 XML —— 否则程序根本起不来

这是踩过的坑，改这个文件前务必先读。特征症状：

```
应用程序无法正常启动，因为应用程序的并行配置不正确。
```

也就是 Windows 错误 **14001（`ERROR_SXS_CANT_GEN_ACTCTX`）**。它意味着 SxS 加载器
**拒绝了 exe 里嵌的那份清单**，进程在托管代码执行之前就被杀掉，所以日志里什么都看不到，
只会弹一个完全不提清单的报错框，极难定位。

**真正的元凶：XML 注释里出现了双连字符 `--`。** XML 规范明确禁止
（"XML 注释中不能包含 `--`，并且 `-` 不能是最后一个字符"）。
错误清单里那条注释写的是：

```xml
<!--
  这样 --selftest / --no-elevate 两个诊断参数才能在不触发 UAC 的情况下运行。
-->
```

那两处 `--` 让整份清单变成非法 XML，SxS 解析失败 → 14001。

**已实测排除的（都不是原因，不必再怀疑）：**

| 变量 | 结论 |
| --- | --- |
| 中文 / 非 ASCII 字符 | 无关。把注释里的中文全部换成 `x` 后**依旧** 14001 |
| 缺 `type="win32"` 的 `<assemblyIdentity>` | 合法，加了也通过 |
| `<dpiAware>` / `<dpiAwareness>`（含 `true/pm`） | 合法，通过 |
| `<longPathAware>` | 合法，通过 |
| `<application><windowsSettings>` 混合三套命名空间 | 合法，通过 |

只用 `CreateActCtx` 探针逐个验证过：**把旧清单原封不动、仅把 `--` 改成 `- -`，SxS 立刻接受**。

**所以约束是：**

- **清单里不要写包含 `--` 的注释**——最省事的做法就是压根不写注释（想说明就写进本文档）。
- 任何改动之后都要能通过 XML 校验。`build.bat` 已经内置这一步，非法 XML 会**直接中止构建**，
  不会再产出启动不了的 exe。手动自查可以用：
  ```
  powershell -NoProfile -Command "[xml](Get-Content -Raw app.manifest) | Out-Null; 'XML 合法'"
  ```

**为什么当前清单这么短：** 只保留两段最不含风险的内容——`trustInfo`（`asInvoker`，提权由程序
启动时自行重启完成）和 `compatibility`（声明支持 Win10 / Win8.1）。既然实测已经证明其余段落
都合法，将来想加回 `assemblyIdentity`、`longPathAware` 之类是可以的，加上后记得跑一遍 `build.bat`。

**高 DPI 刻意不写在清单里。** 清单里放 `dpiAware` / `dpiAwareness` 会触发编译警告
`WFO0003`（WinForms 官方已改为推荐用 API），所以 DPI 感知统一由 `Program.cs` 里的
`Application.SetHighDpiMode(HighDpiMode.PerMonitorV2)` 负责，并把返回值写进日志备查。
本程序全程按物理像素坐标工作，必须是 PerMonitorV2；正常日志里应能看到：

```
SetHighDpiMode(PerMonitorV2) => True
```

### 万一还是起不来：怎么拿到真正的错误

这类启动期失败发生在托管代码之前，`%APPDATA%\HoldDrag\holddrag.log` 里**不会有任何记录**。
要用 Windows 自己的工具拿错误详情：

```
sxstrace.exe Trace -logfile:sxs.etl
（然后双击运行 HoldDrag.exe，复现失败）
sxstrace.exe Trace -stop
sxstrace.exe Parse -logfile:sxs.etl -outfile:sxs.txt
```

`sxs.txt` 里会直接写明是哪一行、哪个元素有问题。也可以看「事件查看器 → Windows 日志 → 应用程序」
里来源为 `SideBySide` 的条目。

另外，`bin\Release\net10.0-windows\win-x64\` 下那套**多文件**产物（`HoldDrag.exe` + `HoldDrag.dll`
+ 两个 json，四个文件放同一个目录直接运行）是一条备用路径：它能绕开单文件打包，用来判断
问题出在清单还是出在打包。

## 拖动跟手是怎么保证的 —— 三个真实踩过的坑

这一节记录的是"窗口跟不动""有些软件用不了"那两次返工查出来的东西。三条都属于
**看起来能跑、实际必然出问题**的写法，将来改拖动相关代码请先读这里。

### 坑一：低级鼠标钩子里**绝对不能**吞掉 `WM_MOUSEMOVE`

**症状：** 长按触发键、窗口确实变半透明了，但鼠标拖出去一段距离，窗口只在原地抖。

**原因：** 在 `WH_MOUSE_LL` 钩子里对 `WM_MOUSEMOVE` 返回非零值（= 吞掉），系统会认为这次移动被拒绝
—— **光标就停在原地不动了**。光标不动，钩子下一帧拿到的坐标自然也不变，
于是窗口只能跟着在原地哆嗦。这不是"移动没生效"，而是"根本没有新的坐标进来"。

对照 AltSnap 的 `LowLevelMouseProc`：它在鼠标移动分支上**始终** `CallNextHookEx`，
从不吞掉移动消息。驱动拖动的是坐标本身，跟"要不要放行这条消息"完全是两件事。

**结论：** 拖动期间鼠标移动消息一律放行。回归用例是 `T20 拖动期间绝不吞鼠标移动`，
它同时断言"一次都没被吞"和"窗口严格跟到最后一个位置"。

> 顺带删掉了配置项 `SwallowDragMouseMoves`。它是当初我自己加的，把"要不要吞掉消息"和
> "要不要用消息驱动拖动"捆在了一起，怎么调都是错的。老配置里残留的该字段会被直接忽略，不影响加载。

### 坑二：**不能**用 `GetAsyncKeyState` 校验"触发键还按着没有"

**症状：** 按住了触发键，功能时灵时不灵——大约每两秒会失灵 0.6 秒。

**原因：** 长按方案必须主动吞掉触发键的按下事件（否则会漏一个 Enter 给前台程序）。
而事件一旦被吞，**系统层面就完全看不到这个键被按过**。原来的看门狗每 2000 ms 用
`GetAsyncKeyState` 检查一次，于是每次都得出"抬起事件丢失了"的错误结论，
把激活态打掉；要等键盘自动重复的下一个按下事件重新计时 600 ms 才能恢复。

这不是推理，是实测。探针在 `_diag/KeyStateProbe`，结果一目了然：

```
── 场景 1：钩子里【吞掉】F13 的按下 ──
  按下后：GetAsyncKeyState=0x0000  [当前按下=否]      ← 钩子确实被调用了 1 次，但状态是 0
── 场景 2：钩子【放行】F14 的按下（对照组）──
  按下后：GetAsyncKeyState=0x8001  [当前按下=是]      ← 同一时刻，放行的键就能读到
```

**结论：** 看门狗已删除。状态机改成纯事件驱动，并且**本身就能自愈**：万一真的丢了抬起事件，
`_held` 仍是 true，用户再点一下触发键也只会被吞掉（不会重复激活），紧接着那一次正常的抬起
就会把状态清干净。回归用例是 `T23 触发键激活态稳定保持`（按住 2.5 秒，激活态必须一直在）。

### 坑三：钩子会被 Windows **静默摘除**——这才是"有些软件用不了"的真正原因

**症状：** 部分软件上完全没反应，或者用着用着突然失灵，重启程序又好。看起来很像"兼容性问题"，
于是很容易往"这个窗口特殊"的方向去查，实际上跟目标软件一点关系都没有。

**原因：** Windows 给低级钩子设了一个超时（`LowLevelHooksTimeout`）。钩子回调只要在规定时间内
没返回，系统会**直接把钩子摘掉**，而且——按微软文档的原话——**没有任何办法得知钩子已经被摘除了**。
没有回调、没有返回值、没有事件。程序完全蒙在鼓里，钩子线程还在跑，只是再也不会被叫到。

什么时候会超时？钩子回调里做了任何稍重的事：`EnumWindows`、`AttachThreadInput`、
`ForceForeground`、甚至只是目标窗口那一刻正好卡在自己的消息循环里。所以表现是**随机**的，
而且**越是多开、越是系统忙，越容易触发**——正好符合"有些软件用不了""用着用着就不灵"。

**现在的做法：看门狗 + 自动重装**（`HookWatchdog.cs`，抄的是 AltSnap 的 `REHOOK_TIMER` 思路）：

```
每 1000 ms 检查一次
  GetCursorPos()  拿到的系统光标位置
  vs  钩子最后一次收到的位置（HookEngine.MarkSeen 记录）

光标动了，但钩子那边位置没动  →  钩子已经死了
  → UnhookWindowsHookEx + SetWindowsHookEx 重装
```

判据本身很朴素：钩子活着的话，你动鼠标它就一定会被叫到。它没被叫到，就是死了，没有第二种解释。
自检里 `T28` 会真的把钩子卸掉、动一下鼠标，再看门狗有没有把它装回来——不是推理，是跑出来的。

**顺带一起修的通用性问题：**

| 问题 | 处理 |
| --- | --- |
| 钩子回调里干重活 | 提前景、枚举窗口全部 `Post` 到工作线程，钩子线程只判断 + 投递就返回 |
| 全屏/无边框窗口被拖完一片黑 | 这类程序不是消息驱动的，被第三方 `SetWindowPos` 之后往往不重画。默认**跳过**，需要时在设置里开「允许拖动全屏/无边框窗口」 |
| 个别顽固程序怎么都拖不动 | 设置里填「不生效的窗口（黑名单）」，命中标题或程序名就完全不接管，给它一个明确的排除口 |
| 被完全遮住的窗口参与边框对齐 | `EnumWindows` 的枚举顺序是从上到下的 z 序，用它排除被盖住的窗口，不会对到一个看不见的窗口上 |

> 托盘图标上能看到看门狗的累计检查次数和救援次数。如果你发现"救援次数"在持续上涨，
> 说明系统里有别的东西在拖慢钩子回调，那就是该查的方向了。

### 配套改动：钩子回调搬去工作线程

微软 `LowLevelMouseProc` 文档明确要求：钩子回调必须"把工作交给 worker 线程后立刻返回"，
因为回调耗时一旦超过 `LowLevelHooksTimeout`，Windows 会把钩子**静默摘除**，
而且**没有任何 API 能告诉我们它被摘了**。原来的写法在钩子回调里做 `EnumWindows`（还逐窗口取类名）
再 `SetWindowPos`，是最典型的会超时的写法。

现在照 AltSnap 的 `WorkerThread` 结构改成了：

```
钩子线程                         工作线程 (DragWorker)
────────                         ──────────────────────
按下/抬起 → 开合会话              收到 WM_DOMOUSEMOVE →
移动     → PostThreadMessage ───→   把队列里堆积的移动【全部丢掉，只留最新的一个】
（立刻返回，绝不做重活）            算矩形 → SetWindowPos → 更新浮层
```

"只执行最新位置"这一条是 AltSnap 有意为之的：窗口永远追最新坐标，不会因为积压而一顿一顿。
而位置算法本身用的是「**当前光标 − 拖动开始时的固定偏移**」（AltSnap 的 `posx = pt.x - state.offset.x`），
是**绝对推导、不做增量累加**，所以哪怕丢事件也不会产生累积漂移。
日志里能看到合并确实在发生：

```
TRC  合并掉了 60 个过期的鼠标移动位置
TRC  移动 光标=480,330 期望=320,220 320x220 实际=320,220 320x220
```

写窗口的标志位照抄 AltSnap 的三档策略（`WindowActions.SetDragRect`）：

| 情况 | 标志 | 说明 |
| --- | --- | --- |
| 尺寸变了 | `RESIZEFLAGS` | `SWP_ASYNCWINDOWPOS` + `SWP_NOCOPYBITS`：异步不阻塞；同时禁止系统把旧像素复制/拉伸到新尺寸，避免缩放残影 |
| 只是平移、窗口可缩放 | `MOVETHICKBORDERS` | `SWP_NOSIZE`，同步写（系统 copybits 整窗搬移，最丝滑） |
| 只是平移、窗口不可缩放 | `MOVEASYNC` | 再加 `SWP_ASYNCWINDOWPOS`（同步写对这类窗口有概率卡死） |

`WM_SYNCPAINT` 只在缩放路径下发，且超时只有 8ms：它只是一条"请尽快重绘"的提示，
等 120ms 反而会让慢窗口每帧把工作线程堵住。
纯平移不发 `WM_SYNCPAINT`，强迫目标窗口逐帧重绘就会看到"字在抖"。

另外进入/退出拖动时会向目标窗口发 `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE`
（`WindowActions.NotifySizeMove`），终端模拟器一类程序靠这个切到字符网格对齐模式，
不发就会在拖动时抖得很难看。

### 拖动期的外框为什么是"区域环"

拖动进行中亮在目标窗口四周的是 **DragRingFrame**（`SetWindowRgn` 抠出的纯色圆角环），
不是抗锯齿分层框（ActivationFrame）。这是"缩放不跟手、外框拖残影"的真正解法：

- 分层位图框每动一帧都要 `UpdateLayeredWindow` 重新上传**整张窗口大小的位图**，
  缩放时甚至每帧重建 GDI+ 位图——窗口越大越卡，环永远慢窗口半拍，看起来就是甩不掉的外框残影；
- 区域环纯平移 = 一次 `SetWindowPos`（系统 copybits，零重绘零上传）；
  缩放 = 一次 `SetWindowPos` + 一次 `SetWindowRgn`（几微秒的 GDI 调用）；
- 环的写入由工作线程**同步直写**（`SWP_NOSENDCHANGING`，不和窗口发同步消息），
  与 `SetWindowPos` 同一拍落地，永远贴着窗口；
- 松手后（触发键还按着）换回抗锯齿分层框——静止时看的仍是平滑的弧。
  快速拖动中 1px 的区域锯齿人眼基本无感。

## 高 DPI 下"所有选项全部重叠"：根因与修法

这是本项目踩得最深的一个坑，值得单独记一节，因为它**在 100% DPI 的机器上
永远复现不了**，只在 125%/150%/200% 的屏幕上出现。

### 症状

用户报："设置里面的这些选项都重叠在一起了呀。"

具体表现是每个分组里的复选框/标签行行相叠，文字互相压在一起，整屏没法看；
而同样的代码在 100% 缩放的机器上完全正常。

### 根因：`AutoScaleMode.Dpi` 与"布局基准"的坐标系错位

本窗口所有控件的坐标和尺寸都是**代码里写死的设计稿值**（96 DPI 基准）：

```csharp
g1.Controls.Add(Label("触发键", 16, 31, 60));   // 96 DPI
var g4 = Group("拖动与吸附", 0, 0, GroupWidth, 230);
```

而原来的窗体设了：

```csharp
AutoScaleMode = AutoScaleMode.Dpi;
AutoScaleDimensions = new SizeF(96f, 96f);
```

WinForms 会在窗体**第一次显示**时执行 `PerformAutoScale()`，把子控件的
`Left/Top/Width/Height` 统统乘以 DPI 系数。200% 屏上 `Top=110` 的控件
会变成 `Top=220`。

**而 `MarkBase()` 是在构造函数里采基准的 —— 那是缩放之前。**
于是：

```
基准 BaseTop = 110          （96 DPI 设计稿）
实际屏幕位置 = 220           （已缩放）
```

接下来布局代码干的事是：

```csharp
c.Top = it.BaseTop + dy;     // 拿 110 去覆盖 220
```

每一行的 Y 都被"缩"回去一截。行距 26 变成 13，而字体是实打实放大到 200% 的，
行与行随即咬在一起。更糟的是"谁和谁同行"的判断也用 `BaseTop`，
于是判定全部失准，叠上加叠。

> 一个反直觉的细节：实测在这台机器上，**字体被放大了，但控件 bounds 没有等比放大**
> （因为位置是代码显式赋的），于是出现"字变大、行距没变"这种半吊子状态。
> 所以后来试过"事后重新采样基准"（`RebaseAfterAutoScale`），靠行距比值反推系数 ——
> 那个系数是 1.0，等于白改。这才逼出下面这个彻底的解法。

### 修法：关掉自动缩放，自己做一次显式缩放

```csharp
AutoScaleMode = AutoScaleMode.None;      // 不再让 WinForms 插手
ScaleDesign(g1, g2, g3, g4, g5, g6);     // 在 MarkBase 之前，按 DPI 缩放全部设计稿值
```

`ScaleDesign()` 做四件事，顺序不能换：

1. 分组框的 `Size` 按 `DeviceDpi/96` 缩放；
2. 组内每个控件的 `Location` / `Size` 缩放；
3. **卡片标题字号**按像素缩放（`TitleFontPx`，单位是像素，不缩会比正文还小）；
4. 继承自窗体的字体按比例放大（只放大"和窗体同字号"的，避免放大两次）。

然后才是 `MarkBase()` —— 采到的基准已经是"当前 DPI 的真实坐标"，
**基准即实际，坐标系从根上只有一套**。

配套地，所有布局常量也改成按 DPI 缩放的实例属性：

```csharp
private int GroupWidth          { get { return S(536); } }
private int SingleColumnClientWidth { get { return S(560); } }
private int GroupInnerPadLeft   { get { return S(18); } }
private int ScrollEdgeMargin    { get { return S(12); } }
```

窗体默认尺寸、`MinimumSize`、底栏按钮尺寸与间距、两列切换阈值
（`TwoColumnThreshold * CurrentUiScale`）也全部走 `S()`。

### 一个必须守住的约定

> **`MarkBase()` 之后，任何地方都不许再改控件的基准坐标。**
> 布局里凡是出现"基准 + 增量"的写法，增量都必须是"这一轮的总量"而不是"累加量"，
> 否则反复布局会一次比一次偏。

### 同类 bug：断行下推把"自己那行"也推走了

`ApplyRowWraps()` 里累积断行下推量时，判定条件早先写的是 `>=`：

```csharp
if (o.BaseTop >= bumps[b].Key) dy += bumps[b].Value;   // 错
```

`bumps[b].Key` 记的就是**那一行自己的 BaseTop**，用 `>=` 意味着
"断行所在这行"也被推了一次，于是同一行的两个复选框被推到了同一个 Y 上 ——
"双击左键"和"双击右键"两行完全重叠。正确语义只有一条：

```csharp
if (o.BaseTop > bumps[b].Key) dy += bumps[b].Value;    // 严格大于
// 被断下来的那个控件单独挪到 rowY + rowH + 4
```

### 设计令牌

所有颜色收敛到 `SettingsForm.Design`，改主题只改这一处：

| `TextSecondary` | `#7E8491` | 说明文字 |

### `CardGroup : GroupBox`

原生 `GroupBox` 的边框是系统 3D 凹线（etched），在现代扁平界面里非常旧，
而且边框颜色在 200% DPI / 主题切换下不受控。

**为什么派生 `GroupBox` 而不是直接换成 `Panel`：**
整个响应式布局（`ResponsiveGroupPanel` / `MarkBase` / `ApplyRowWraps` /
`GrowGroupsForWraps`，以及自检里一堆 `as GroupBox`）都是按 `GroupBox` 写的，
换掉容器类型等于把这些全改一遍 —— 改动面大、回归风险高，
而这次要解决的是**观感**，不是结构。所以只重写 `OnPaint`，坐标口径原封不动：

- 边框：3D 凹线 → 圆角 + 细描边（半径 10，描边 `#DBDFE7`）
- 底色：系统灰 → 纯白卡片
- **投影**：把圆角轮廓往下偏移 2px、用半透明深色描 5 层边 —— 卡片"浮"起来的关键
- **左侧强调竖条**：3px 靛蓝，按卡片路径裁剪（否则直角会戳出圆角外）
- 标题：画在边框缺口 → 浮在卡片内侧左上角（13px 粗体）

> ★ 上面的圆角/竖条/投影参数**全部要按 DPI 缩放**。
>   上一版就是漏了这一步 —— 200% 屏上圆角只有 10px（正常 20）、竖条 3px（正常 6），
>   投影细得像条线，整张卡片退化回"灰底上一块白方块"，
>   **功能全对但看着跟没改一样**（用户原话："还是跟之前一样，没什么太大区别"）。

> **卡片标题会占用客户区顶部一条**（`TitleInsetPx = 30`）。
> 原生 `GroupBox` 的标题画在边框缺口上、**不占**客户区，所以设计稿里第一行
> 可以从 y=26 开始。改成浮动标题后必须让位，否则"触发键"那几组的标题会压住控件。
> 让位在 `ScaleDesign()` 里统一做（`c.Top += inset`），而不是在 `Group()` 里
> 逐个改坐标常量 —— 那样以后新增控件又得记得加，漏一处就是隐性回归。

### `FlatButton : Button`

派生 `Button` 而非 `Control`，同样是为了不动字段声明和自检代码。
除了自绘圆角背景，还必须关掉系统外观，否则会出现"双边框"：

```csharp
FlatStyle = FlatStyle.Flat;
FlatAppearance.BorderSize = 0;
FlatAppearance.MouseOverBackColor = Color.Transparent;
UseVisualStyleBackColor = false;
```

主次分明：只有"保存并生效"是主按钮（实心强调色 + 悬停/按下反馈），
"恢复默认值"和"取消"是描边次按钮 —— 原来三个按钮长得一模一样，
用户得自己猜哪个是主动作。

`ScaleDesign()` 里还会给按钮单独缩字号：框变大了字没变，视觉上就是"按钮空了一圈"。

### 消除底部空白：`FitHeightToContent()`

用户反馈"设置页面还有很大一部分空白"。根源是窗口高度写死（`S(760)`），
而内容高度**随列数变化极大**：单列时 6 个分组纵向排开可能有两千像素（需要留白+滚动），
两列时摆成 2×3 可能只有七百（留白就是浪费）。

```csharp
int contentH = _groupHost.Height + ScrollEdgeMargin * 2;
if (want > maxH) return;      // 装不下 → 保持并滚动
if (用户自己记过尺寸) return;   // 别把用户拉好的窗口改回去
```

只在 `OnShown` 调一次。**用户手动记过的尺寸绝不覆盖** ——
"记住窗口大小"是明确需求，强行改回去比留白更让人烦。

## Anchor 双重拉伸：控件宽度莫名变成两倍

改完高 DPI 缩放之后又冒出来一个更隐蔽的 bug：
"开机自启"下拉框的设计稿宽度是 430，实际渲染出来却是 **1502**。

### 为什么会多出一倍

时序问题。控件（例如下拉框）在设计稿里带了

```csharp
_cmbAutoStart.Anchor = AnchorStyles.Top | AnchorStyles.Left | AnchorStyles.Right;
```

表示"父容器变宽时跟着右边一起拉宽"。而 `ResponsiveGroupPanel` 在**构造时**
就把分组塞进了 `TableLayoutPanel` 并定好了列宽，于是 WinForms 的锚定逻辑
**在 `ScaleDesign()` 之前**已经把这些控件拉宽过了：

```
设计稿 430 → 【锚定拉伸】→ 751 → 【ScaleDesign ×2】→ 1502
```

我们想要的是：

```
设计稿 430 → 【ScaleDesign ×2】→ 860
```

### 为什么后果严重

多出来的那一倍不是"多了点留白"，而是让右边界算成负数：

```csharp
baseRightGap = BaseInner - (BaseLeft + BaseWidth)
             = 1072 - (180 + 1502) = -610        // 负了
right = innerRight - baseRightGap;               // 于是算出 innerRight + 610
```

控件直接反超分组 602px，选项全被切掉。更隐蔽的是 `LeftBarrier()`
会把这个撑宽后的宽度当成"左边那道墙"，把右边的按钮一路顶出分组 ——
实测"以管理员重启"按钮被推到 `L=1452`，而分组本身才 1072 宽。

### 修法

**在 `ScaleDesign()` 开头先把所有 Anchor 摘掉**：

```csharp
g0.Anchor = AnchorStyles.Top | AnchorStyles.Left;
foreach (var c in g0.Controls) c.Anchor = AnchorStyles.Top | AnchorStyles.Left;
```

敢这么做是因为 `MarkBase()` 里本来就把每个控件的 Anchor 改成 `Top|Left`
（"伸缩完全由 `LayoutInner()` 接管，两边同时作用会算两次"）——
本项目的布局从一开始就不依赖系统锚定，这里只是把摘除提前到缩放之前。

> **通则**：任何"自己接管布局"的代码，都必须先把系统的自动机制摘干净。
> 系统锚定和自绘缩放同时作用，就是双重计算。

### 顺带修掉的三个同类问题

1. **`SetShiftFromRight` / `SetGrowRightNeighbor` 的 gap 没缩放**
   调用方传的是设计稿像素（16、24、10），而 `MarkBase()` 跑在 `ScaleDesign()` 之后，
   基准已经是放大后的坐标系。拿 16 去和放大后的 32 比大小，判定整个反向。
   → 在这两个方法里直接 `S(gap)`。

2. **间隙阈值 `8` / `6` 是硬编码像素**
   断行判定和链式推挤都拿它和放大后的坐标比，不缩放就会在高 DPI 下过松。
   → 改成 `S(8)` / `S(6)`。

3. **`ReserveLabelWidth()` 撑宽时无视右邻约束**
   "当前权限：普通用户（日常窗口没问题）…"在 200% 下量出 1408px，
   而它右边紧挨着按钮。把 `BaseWidth` 撑到 1408 后 `baseRightGap` 变负，
   标签反超分组 364px。
   → 撑宽上限加上右邻约束，同时给 `_lblAdmin` 补上 `SetGrowRightNeighbor`。

### 截图必须离屏渲染，不能抓屏幕

```csharp
// ❌ 之前：抓屏幕上这块区域此刻长什么样
g.CopyFromScreen(f.Location, Point.Empty, f.Size);

// ✅ 现在：让窗体往离屏位图上画自己
f.DrawToBitmap(bmp, new Rectangle(0, 0, w, h));
```

只要桌面上有任何别的窗口盖在上面（通知气泡、浏览器、IDE 侧边栏…），
截出来就是那个窗口。之前好几张"布局坏了"的截图其实**抓错了对象**，
白排查半天 —— 其中一张我据此判断"按钮跑到分组外面了"，
实际那个按钮是被另一个窗口的残影挡住的。

### 探测尺寸必须按屏幕可用区域算

早先按"设计稿数字 × DPI 系数"开窗口，结果窗口比屏幕还宽，
Windows 把它裁到屏幕宽度，**截出来的图看着像布局坏了，其实只是窗口没开到那么大**；
而且窄档和中档会双双撞上 `MinimumSize`，截出两张一模一样的图。

```csharp
Rectangle wa = Screen.PrimaryScreen.WorkingArea;
int narrow = (int)Math.Round(wa.Width * 0.42);   // 单列刚好放下
int mid    = (int)Math.Round(wa.Width * 0.72);
int wide   = (int)Math.Round(wa.Width * 0.96);   // 两列很宽
```

比例本身就是设计意图，换任何分辨率都成立。

### 幂等性断言

`Dump()` 会连跑 3 次 `LayoutResponsive()` 并逐次比对结果字符串。
**布局代码里凡是 `+=` 累加的地方都会在这里现形**（第二次位置比第一次低一截）。

## 不跟手：平移漏了 SWP_ASYNCWINDOWPOS

用户报"移动窗口和拖拽窗口变形不跟手"。根因在 `Native.cs` 的标志位定义：

```csharp
// 改之前
public const uint MOVETHICKBORDERS = SWP_NOZORDER | SWP_NOOWNERZORDER | SWP_NOACTIVATE | SWP_NOSIZE;
public const uint MOVEASYNC      = MOVETHICKBORDERS | SWP_ASYNCWINDOWPOS;
```

`MOVETHICKBORDERS` **漏了 `SWP_ASYNCWINDOWPOS`**（只有 `MOVEASYNC` 有）。
缺这个标志时，`SetWindowPos` 会**同步等**目标窗口处理完
`WM_WINDOWPOSCHANGING` / `WM_WINDOWPOSCHANGED` 才返回 —— 目标窗口越复杂、
越是跨进程（浏览器 / IDE / 资源管理器），等待越久，拖动工作线程每帧都被堵住，
表现就是"窗口追不上鼠标"。

症状特征：**平移比缩放更明显**。缩放走 `RESIZEFLAGS`，本来就带 ASYNC；
而平移走 `MOVETHICKBORDERS`，只能干等。

讽刺的是，`WindowActions.SetDragRect` 上方的注释第4 点写着
"平移（MOVETHICKBORDERS / MOVEASYNC）只用 SWP_ASYNCWINDOWPOS"——
**注释和实现自相矛盾**，注释是对的，代码漏了。

修法：`MOVETHICKBORDERS` 补上 `SWP_ASYNCWINDOWPOS`，`MOVEASYNC` 随之简化。

T42 断言三套标志位都带 ASYNC，且平移不带 `NOCOPYBITS`
（那个是缩放专用的，用在平移上会让 DWM 不搬运像素，窗口内容跟不上位置 → 花屏）。

## 底栏按钮的文字与框没适配

用户原话："恢复默认值、保存并生效、取消这几个按钮字跟这几个按钮并没有进行很好的适配"。

两个独立原因：

**1. 用错了度量 API。** `FlatButton.OnPaint` 原来这样画文字：

```csharp
var sz = g.MeasureString(Text, Font);                      // GDI+ 的度量
float x = (Width - sz.Width) / 2f;
float y = (Height - sz.Height) / 2f - 1;                  // ← 手工减的 1，纯凭感觉
TextRenderer.DrawText(g, Text, Font, new Point((int)x, (int)y), fg, ...);  // GDI 的绘制
```

`MeasureString` 是 GDI+、落笔的是 `TextRenderer`（GDI/Uniscribe），
两套 API 的字形宽度与行高基准都不一样。用 A 的度量推算 B 的位置，高 DPI 下
偏差被放大成"字偏出去、和框不搭"。

正解：把整块矩形交给 `TextRenderer`，让它自己按
`HorizontalCenter | VerticalCenter` 对齐 —— 它内部用的度量跟绘制是同一套，
天然对齐。

**2. 按钮高度和同排输入框不在一个尺度上。** 设计稿里按钮 32 高、输入框 26 高；
200% 下分别是 52 和 39（ComboBox 有内部留白，实际渲染高度不等于设定值）。
断言直接量出：`按钮高 52 输入框高 39 差 13`。

改成 20（→ 40），与 ComboBox 实际渲染高度对齐；底栏 `_pager` 也跟着从
`S(58)` 降到 `S(46)`（按钮 26 + 上下各 10）。

另外按钮圆角原来写死 `6`，没跟 DPI 缩放 —— 框变大了圆角还是那么点，
视觉上跟卡片组的圆角完全不是一个语言。改成 `6 * CurrentUiScale`。

> **通则：自绘控件里，凡是用 A 算、用 B 画，就是隐患。
> 交给同一个 API 去做"度量 + 绘制"，并让它的对齐标志负责居中。**

## 下拉框显示为空但点开有选项

用户原话："外框形状选项里面显示是空的，但是我点开里面却又有好几个选项"。

机制：`ComboBox.DropDownStyle = DropDownList` 时，**框里显示什么完全由
`SelectedIndex` 决定**。一旦它停在 `-1`，框就是空白；而下拉列表里各项都还在
——`Items` 集合和"当前选中态"是两回事。

什么情况下会停在 `-1`：`Items.Clear()` 会把 `SelectedIndex` 重置成 `-1`，
如果清空之后没能成功选中任何一项，就会留下这个状态。

加固：`SelectId` / `SelectAction` 明确"永远至少选中一项"，
并在设完索引后补一刀 `if (c.Items.Count > 0 && c.SelectedIndex < 0) c.SelectedIndex = 0;`

T41 覆盖两条路径：正常加载（且刻意用**非默认**配置 `Dashed`/`Mint`/
`Custom`/`None` —— 默认值恰好等于第一项，"碰巧就对了"测不出匹配逻辑）
+ "恢复默认值"重建 Items 之后。

## 新增回归用例

### T38：设置窗口所有控件可见可点

改自绘卡片 / 扁平按钮之后加的。**靠断言布局逻辑的那批用例全都发现不了
"控件看不见 / 点不到"这类问题** —— 因为代码里一个异常都不会抛，
界面上就是"某个选项不见了""按钮没反应"。

做法：深度遍历全部后代控件，断言

- `Visible && Width > 0 && Height > 0`（看得见）
- 与所属容器的 `ClientRectangle` 有交集（在容器内，点得到）

一个坑：**"被禁用"绝大多数是设计如此**（外框没开 → 颜色/样式禁用、
已是管理员 → "以管理员重启"禁用）。这些不能判失败，否则测试长期红着，
最终没人看它。要抓的是"本该能用却点不到"。

### T28 加固：钩子看门狗用例的时序竞态

这个用例原本会**偶发假红**（同一份代码连跑三次红 1~2 次）。原因：

`SetCursorPos` 只是改了光标位置，返回时低级钩子事件**未必已经送到**钩子线程。
紧接着调 `CheckOnce()`，看门狗读到的还是"光标没动过" → 判定"钩子还活着"。

这是**用例自身的时序脆弱**，不是被测逻辑有问题（真实场景里光标由人持续移动，
时间窗口充足）。修法是补消息泵 + 重试：

```csharp
for (int attempt = 0; attempt < 12 && !rescued; attempt++)
{
    Native.SetCursorPos(cur.X + 11 + attempt * 3, cur.Y + 9 + attempt * 2);
    for (int k = 0; k < 4; k++) { Application.DoEvents(); Thread.Sleep(25); }
    rescued = wd.CheckOnce();
}
```

一个长期偶尔飘红的测试，久了就没人信它了。

### T39：外框亮着时，鼠标键依然要能接管窗口

针对用户报的**核心功能失效**："长按 enter 到了触发阈值之后，左键按住能移动
窗口、右键能改长宽 —— 这个功能没有了"。

**为什么以前测不出来**：`DragFixture` 里有两行正好把这个 bug 藏起来了：

```csharp
c.ShowActivationFrame = false;                       // 外框是关的
WindowActions.ForcedTargetForTest = Window.Handle;   // FindTarget 被整个短路
```

也就是说历史上所有端到端用例都跑在"外框关着 + 不查真实命中"的组合下，
而"外框开着"这条路径**从来没被执行过**。bug 就住在那里。

所以本用例刻意不走 `DragFixture`：自己建窗口、`ShowActivationFrame = true`、
`ForcedTargetForTest` 保持 `IntPtr.Zero`，全程走真实 `WindowFromPoint`。

一个配套的测试钩子（`WindowActions.SetForeignForTest`）：把指定 hwnd
当成"别的进程的窗口"。因为测试窗口和浮层同属本进程，不这样处理的话，
`AllowOwnProcessAsTargetForTest` 会直接把整段穿透逻辑短路掉，等于没测；
而真去起一个外部进程在受限环境里又起不来。

顺带在用例里打一行诊断，把"浮层到底压没压住光标"写进报告
（实测 `WindowFromPoint` 命中的是目标窗口，说明浮层并没有抢走命中——
这一点原来靠猜，猜错了）。

### T40：高 DPI 下文字不被裁切

针对"两列那个图里面字体被遮住了呀，被遮住了一半"。

**根因：字号被放大了两次。**

```
Point 单位的字号，系统已经按当前 DPI 换算过像素高度了：
    9pt @ 96dpi  = 12px
    9pt @ 192dpi = 24px   ← 系统自动放的，已经是设计稿的 2 倍
代码里再乘一次缩放系数 s：
    18pt @ 192dpi = 48px
而控件高度只放大 2 倍（20 → 40px）
    → 字高 48px 装进40px 的框 → 被裁掉一半
```

实测数据：`字高79 > 框高44`。

正确分工：

|东西 | 谁负责 |
|---|---|
| 控件 bounds | 我们手动乘 `s`（因为 `AutoScaleMode=None`，系统不管） |
| 字号 point | 系统按 DPI 自动换算（**我们什么都不用做**）|

> **通则：改成 `AutoScaleMode.None` 之后，只有"代码写死的坐标"需要手动缩放，
> 字号绝对不要碰。** 这是"自己接管缩放"最容易多算一次的地方。

断言方式：拿每个控件**实际渲染出来的文字高度**（`Graphics.MeasureString`
+ 行距余量）跟它的**实际高度**比，而不是看字号数字 —— 因为 Point 字号
和像素高度是两套换算，看数字判断不出来。

### 诊断：为什么"按了没反应"以前完全查不出来

用户报"功能失效"时，日志里只有 `触发键激活` / `触发键释放`，中间一片空白。
原因是 `Coordinator.HandleButtonDown` 里两条 `return false` **全是静默的**：

```csharp
if (action == Actions.Nothing) return false;                        // 静默
IntPtr hwnd = WindowActions.FindTarget(pt, ...);
if (hwnd == IntPtr.Zero) return false;                              // 静默
```

而 `FindTarget` 有一长串拒绝条件（黑名单 / 类名 / 全屏 / 自身进程 / 尺寸为 0），
命中任何一条用户体验都是"按下去没反应"，日志一个字都不留。

修法：`WindowActions.DescribeReject(pt, allowFullscreen)` 把每一条判定
按**与 `FindTarget` 严格相同的顺序**复现一遍，报出卡在哪一条
（"窗口占满整个显示器""命中黑名单""类名被排除""命中的是全屏播放器"…），
在两个 `return false` 前各记一行 `Log.Trace`。只在 `--trace` 打开时输出，
不影响热路径性能。

> **通则：用户报"按了没反应"这类问题时，第一件事是确认失败路径有没有留日志。
> 静默的失败路径会让排查彻底失去方向。**

### `FindTarget` 的 Z 序穿透加固

浮层是 `WS_EX_TOPMOST + WS_EX_LAYERED`，长按触发键后就压在目标窗口上方。
而 `WindowFromPoint` **不会给窗口发 `WM_NCHITTEST`**，所以浮层里那套
"返回 `HTTRANSPARENT` 实现点击穿透"对它无效 —— 它照样会把浮层自己返回来。

所以 `FindTarget` 改成：命中自己就沿 Z 序用 `GetWindow(h, GW_HWNDPREV)`
继续往下找，直到找到第一个不是自己的窗口（上限 32 层防打转）。

> 诚实备注：实测下来 `WindowFromPoint` 多数时候命中的还是目标窗口本身，
> 所以这条**不是**用户那次失效的根因，属于防御性加固 ——
> 但"自己的浮层压在目标上面"这个前提一旦成立（不同 DPI、不同 Z 序、
> 浮层画得更大），老逻辑就会直接放弃拖动。

## 开发期视觉核对（`--visualcheck`）

布局类改动光靠断言不够：断言能验证"逻辑对"，验证不了"看起来对不对"。

### 探测尺寸必须按屏幕可用区域算

早先按"设计稿数字 × DPI 系数"开窗口，结果窗口比屏幕还宽，

而且窄档和中档会双双撞上 `MinimumSize`，截出两张一模一样的图，

```csharp
Rectangle wa = Screen.PrimaryScreen.WorkingArea;
```

## 设置窗口的两列布局是怎么做到"拉宽真的有用"的

用户反馈过两轮："设置页面被莫名其妙拉宽了很多，拉宽并没有给拉宽的部分增加文字，这种拉宽毫无意义"。
这一版把两列布局彻底做干净了，下面是它的模型。

### 列数切换

宽度 ≥ 1240px 时分组自动从 1 列变 2 列（`ResponsiveGroupPanel.TwoColumnThreshold`）。
阈值不能只看"两列排得下"：本机 125% 缩放，中文标签比设计稿宽 25%
（"缩放角区"要从 66 撑到 114），一列窄于 620 就会出现"只显示一个字"。

### 三个必须同时成立的机制

| 机制 | 解决的问题 |
| --- | --- |
| **文字保底加宽**（只加宽、不推移） | 125% DPI 下标签放不下自己的文字（"缩""长按""吸附距"缺字） |
| **链式右推**（`PropagatePush`） | 标签被撑宽后压到右边紧邻的控件，必须把它带走，否则重叠 |
| **断行**（`ComputeRowWraps` + `ApplyRowWraps`） | 一行并排两个复选框放不下时，右边那个换行独占整行（等价 `flex-wrap`） |

### 几条容易写错的地方（都是实测踩出来的）

1. **CheckBox 的宽度必须用 `PreferredSize` 量。**
   用 `TextRenderer.MeasureText(text) + 常数` 会恒定少 10~17px，正好切掉最后一个字。
   （`AutoSize=false` 时 `CheckBox.PreferredSize` 依然是有效的，含勾选框与内边距。）

2. **"同一水平线"不等于"同一条流水线"。**
   设计稿里 `x=248` 的"样式"和 `x=18` 的"外框颜色"在同一行，
   但它们各自带自己的输入框，中间隔着几百像素 —— 没有任何理由因为左边标签变宽就一起挪。
   所以整行聚类推移的做法是错的，必须"谁真的被压住才推谁"。

3. **判"同行"要用"重叠过半"，不能用矩形相交。**
   设计稿行距 29px，而 125% DPI 下控件本身就有 30+ 高，矩形天然咬进去几像素，
   会把下一行误判成同行 —— 后果是右上角那组控件被一道几百像素外的"墙"顶飞。
   ```csharp
   int ov = Math.Min(bottom, oBottom) - Math.Max(top, oTop);
   if (ov <= 0 || ov * 2 < Math.Min(c.Height, o.Height)) continue;   // 不足半行 → 不算同行
   ```

4. **基准坐标和实时坐标绝不能混用。**
   `LeftBarrier` 一度用 `BaseLeft`（基准）判水平、用 `c.Top`（实时）判垂直，
   而断行的多轮试探会让 Y 来回变 —— 于是算出一道根本不存在的"墙"。
   要么全用 `BaseXxx`，要么全用实时，一半一半必然出玄学 bug。

5. **复选框的高度必须钉死。**
   被压窄时 WinForms 会自动折行、把 `Height` 从 22 涨到 44，
   而 `Height` 是"谁和谁同行"的依据 —— 隐形变化会把整行带偏。
   常规情况钉回 `BaseHeight`；真的独占整行仍放不下（如 733px 的长句）才放行折行，
   并把它下面的行整体下推（`SyncWrappedHeights`）。

6. **宽度下限本身要有上限。**
   给"不得窄于文字"加下限时，下限必须被这一行真正能给的宽度夹住，
   否则 1030px 的整行说明会被撑到 1030px、冲出分组。

### 迭代到不动点

断行判定 ↔ 分组宽度 ↔ 滚动条 ↔ 内容高度 是一个环。
`MeasureAndWrap()` 反复跑【排布 → 判定 → 撑高】直到"断行集合"不再变化
（上限 4 轮，实测 2 轮收敛）。中途**绝不落地中间状态** ——
一度为"先定列数"多调了一次 `Relayout()`，那个中间宽度比真实值大 17px，
`ApplyOne` 读到的 `ClientSize` 是假的，右列控件全被压成 20px。

## 与 AltSnap 的差异

**保留并复刻的**：左键=移动、右键=缩放（九宫格就近角）、中键=最大化/还原、拖动边缘吸附、窗口边框互相对齐、双击左键最大化、双击右键九宫格吸附、可选的动作（移动/缩放/最大化/最小化/关闭/置底/置顶/居中）。

**拖动内核是照着 AltSnap `hooks.c` 复刻的**，不是另起炉灶：`WorkerThread` 的移动事件合并、
`MouseMoveNow` 的「光标 − 固定偏移」绝对定位、`MoveWindowNow` 的三档 `SetWindowPos` 标志、
异步移动后补 `WM_SYNCPAINT`、以及 `NotifySizeMoveStaEnd` 的 `WM_ENTER/EXITSIZEMOVE` 通知，
都能在 `DragWorker.cs` / `DragEngine.cs` / `WindowActions.cs` 里一一对上。
本程序唯一真正新增的东西就是**可自定义的触发键 + 长按阈值**。

> 说明：AltSnap 是纯 C / Win32，本项目是 C# / .NET，"提取"在工程上只能是**逐条复刻它的算法与调用序列**，
> 没法把 C 代码直接搬过来。凡是从它那里抄来的实现，代码注释里都标了对应的函数名。

**刻意去掉的**（AltSnap 里那些你用不到的部分）：黑名单配置文件、主题、多语言、自动更新检查、滚轮的音量/透明度/AltTab、窗口卷起(Roll)、去边框(Borderless)、窗口菜单(Menu)、强杀进程(Kill)、进程注入、多实例、托盘图标中键编辑 ini。

**比 AltSnap 更好的地方**：
- 触发键可以是**任意键**并且带**可调的长按阈值**（AltSnap 只支持 Alt/Ctrl/Shift/Win 组合）。
- 短按补发机制让触发键可以放心用 Enter 这类高频按键。
- 全部设置一个窗口、中文界面、保存即生效，不需要手动编辑 ini。

**不如 AltSnap 的地方**：没有它那套多年打磨的、内置几百条规则的窗口兼容性黑名单。这里改成让你自己在设置里填关键字（「不生效的窗口」），命中就完全不接管。规则少，但胜在能针对你这台机器上真正有问题的程序来排除。

```
第  240 次拖动后：          句柄=660  GDI=119  USER=72  私有=49MB  工作集=101MB
第  320 次拖动后：          句柄=660  GDI=119  USER=72  私有=116MB 工作集=200MB
第  400 次拖动后：          句柄=660  GDI=119  USER=72  私有=49MB  工作集=101MB
第  480 次拖动后：          句柄=660  GDI=119  USER=72  私有=49MB  工作集=101MB

收干净后（含 LOH 压缩，取 3 轮最低值）：句柄=660  GDI=119  USER=72  私有=51MB

  [PASS] GDI 对象没有随拖动次数增长（峰值增量 2）
  [PASS] USER 对象没有随拖动次数增长（峰值增量 4）
  [PASS] 系统句柄没有随拖动次数增长（峰值增量 4）
  [PASS] 私有内存没有随拖动次数增长（看收干净后的底）：底增量 +1 MB
```

**内存判定为什么要"取 3 轮最低值"**：同一份代码连续跑，单次采样会在
`-52MB` 和 `+77MB` 之间跳 —— 那是 .NET gen2 / LOH 段的 GC 锯齿
（第 320 次那格飙到 116MB、下一格又掉回 49MB，一眼就知道不是泄漏）。
所以断言改成"回收 3 轮、取最低值当底"：
**真泄漏会让每一轮都回不去，最小值照样往上抬；锯齿只会让某些轮偏高，最小值始终稳。**
判据是"底有没有抬"，不是"中途抓到多高"。

句柄 / GDI / USER 三条曲线全程平（+2 / +0 / +4），这才是"没有泄漏"的直接证据。

另外 `--smoke`（完整正常启动：托盘 + 钩子 + 2 秒后开设置窗口 + 9 秒后自动退出）退出码 0，
结束后**没有任何残留进程**。
