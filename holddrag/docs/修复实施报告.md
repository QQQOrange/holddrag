## 三、问题一：设置页面无法被拖动

### 3.1 根因

目标窗口解析在 `WindowActions.FindTarget`（L22379）里做，核心循环 L22387–22410：

```csharp
for (int i = 0; i < 32; i++) {
    num = Native.GetAncestor(num2, 2u);            // 命中窗口的顶层根窗口
    Native.GetWindowThreadProcessId(num, out var pid);
    if (((pid != (uint)OwnPid) | flag) || AllowOwnProcessAsTargetForTest)
        break;                                      // ★ 只有“别的进程”才接受
    num2 = Native.GetWindow(num, 2u);               // 本进程窗口：沿 Z 序往下换一个再试
    num = IntPtr.Zero;
}
```

设计意图是让浮层（`HoldDragOverlayWindow`）和托盘隐藏窗口永远不成为拖动目标。但这条判断没有区分「我们自己的浮层」和「我们自己的正常窗口」，于是设置窗口被一并排除。被排除后行为是**静默换目标**而不是报错：

- 设置窗口下面还有第三方窗口 → 拖动的其实是背后那扇窗（探针实测：光标在本进程全屏窗口上时 `FindTarget` 返回 68106，即背后的第三方窗口）；
- 设置窗口下面只有桌面/任务栏（`ExcludedClasses` 命中 `Progman`/`WorkerW`/`Shell_TrayWnd`）→ 返回 0，什么都不做。

因此用户看到的现象是"设置页面既不能被拖，框也可能亮在别的窗口上"，而不是明确的失败提示。

### 3.2 为什么自检全绿却没发现

`selftest.txt` 显示 663 项全过。原因是**所有**涉及本进程窗口的用例都显式打开了测试开关：

```csharp
WindowActions.AllowOwnProcessAsTargetForTest = true;   // 见 L8632、L8379、L8419…共 20 余处
```

这个开关只在自检里被置真，生产路径恒为 false。也就是说，"设置窗口能不能拖"这一条恰好被测试开关屏蔽掉了。

### 3.3 修复方案

**推荐做法：按窗口类名放行本进程的"正常窗口"，只排除我们自己的浮层/辅助窗口。**

```csharp
// 1) OverlayWindow.EnsureClass() 里已经注册了类名，把它提为常量
//    (L6574: lpszClassName = "HoldDragOverlayWindow")
internal const string OverlayClassName = "HoldDragOverlayWindow";

// 2) 新增：本进程窗口是否允许作为拖动目标
private static bool IsOwnProcessTarget(nint h)
{
    string cls = Native.GetClassName(h);
    if (cls == OverlayWindow.OverlayClassName) return false;   // 外框浮层
    if (cls == "HoldDrag.Probe.Target") return false;          // 诊断用探针窗口(L3284)
    if (cls.StartsWith("tooltips_class32") || cls == "SysShadow") return false;
    long style = Native.GetWindowLong(h, -16);
    if ((style & 0x10000000) == 0L) return false;              // 必须 WS_VISIBLE
    if ((style & 0x40000000) != 0L) return false;              // 排除 WS_CHILD
    return true;                                               // 设置窗口、未来的其它正常窗口
}

// 3) 循环内的判断改成
if (pid != (uint)OwnPid || flag || IsOwnProcessTarget(num) || AllowOwnProcessAsTargetForTest)
    break;
```

配套建议：

1. **加一个开关**（默认开启），例如 `AppConfig.AllowDragOwnWindows`，给不希望拖自己窗口的用户留退路；现有的"黑名单"只能减少目标、不能增加目标，所以目前用户没有任何绕过手段。
2. **托盘隐藏窗口**要确认类名不在放行范围内（WinForms 的 `NotifyIcon` 窗口是隐藏的，会被 `WS_VISIBLE` 检查挡掉，无需额外处理）。
3. **补回归用例**：把自检里"拖自己的窗口"的用例改成 `AllowOwnProcessAsTargetForTest = false` 再跑一遍；断言"光标在设置窗口上时 `FindTarget` 返回设置窗口的 HWND"，以及"`DescribeReject` 不再返回『命中的全是本进程窗口』"。

**风险与边界**：放行本进程窗口后，拖动设置窗口期间设置窗口自身会持续收到 `WM_NCHITTEST`/重绘；由于按下与抬起都被钩子吞掉，WinForms 不会进入自己的鼠标拖动逻辑，用 `SetWindowPos` 直接移动是安全的。但要注意：若用户在设置窗口内按下并拖动某个滑块，触发键恰好也在按住，程序会"抢"这扇窗口并把它整体移动——这是产品语义问题，建议仅当动作是 `Move`/`Resize` 且指针位于窗口非客户区或按住触发键时才接管，或干脆靠上述开关让用户决定。

## 四、问题二：粗细参数"不生效"

### 4.1 结论分三层，必须区分对待

| 观察面 | 粗细是否生效 | 证据 |
|---|---|---|
| 真实外框（悬停框、拖动中的框） | **生效** | 运行时日志 `外框矩形` 随粗细变化：粗细 6 → 外扩边距 11px，粗细 8 → 12px；端到端抓屏：粗细 1/3/6/7/8 对应外露墨量 544/811/1266/1483/1546 像素 |
| 设置页「样式」缩略图 | **完全不生效（≥3 之后）** | 渲染 `StyleGallery` 后逐字节比对：粗细 = 3/4/6/8 四张图的 MD5 **完全相同**（`c597c139…`）；粗细 1 与之不同 |
| 设置页「实时预览」 | 生效 | 五张预览图 MD5 两两不同 |

你当前配置是 `FrameStyleId = "Dashed"`、`FrameThickness = 8`（`config.json`）。**粗细 = 8 时，整块「样式」区域无论怎么调都一模一样**——这就是"粗细没有变化"最直接的来源。

### 4.2 三处根因

**① 主因：样式缩略图把粗细钳死在 3，并固定了外扩边距。**
`SettingsForm.StyleGallery.OnPaint`，L14356–14400：

```csharp
int num      = Fields.Sc(7);                       // ← 固定外扩边距
int thickness = Math.Min(_thickness, 3);           // ★ 粗细被钳到 3，4..8 全部退化成 3
int radius2   = Math.Min(_radius, 8);
...
FrameStyles.Draw(graphics, rectangle, color, text, thickness, radius2, num);  // L14399
```

`SyncPreview()`（L18616）确实把真实粗细喂给了画廊（`_galleryStyle.Thickness = thickness`），但画的时候被 `Math.Min` 吃掉。原生 12 个样式缩略图几乎全落在 4..8 区间之外，用户在这个区域永远得不到反馈。

**② 次因：环以窗口"可见边缘"为中心画，一半线宽被目标窗口盖住。**
`FrameStyles.Draw` 的原理是把矩形按 `MarginFor(style, thickness)` 内缩后描边：
`MarginFor("Dashed", t) = t/2 + 1 + 7`。而 `DragEngine.FrameRectOf`（L2853）恰好把外框窗口**只放大这么多**：

```csharp
int num = FrameStyles.MarginFor(c.FrameStyleId, c.FrameThickness);
Native.RECT r = visibleRect(windowRect, _inset);      // 去掉 DWM 阴影，实测缩进 11/0/11/11
return new Native.RECT(r.Left - num, r.Top - num, r.Right + num, r.Bottom + num);
```

于是描边路径永远落在窗口**可见边缘**上，线宽向外、向内各分一半：

| 粗细 | 外扩边距 | 外露墨量 | 外扩最大距离 |
|---|---|---|---|
| 1 | 8 px | 544 | 2 px |
| 3 | 9 px | 811 | 3 px |
| 6 | 11 px | 1266 | 5 px |
| 7 | 11 px | 1483 | 5 px |
| **8** | **12 px** | **1546** | **6 px** |

日志里 `抬到最顶=False`（外扩模式下 `_frame.RaiseAboveAll = inset = false`，L2546）意味着浮层在拖动期间**不加到最顶**，目标窗口（`BringToFront = true`）压在它上面，向内的那一半线宽被窗口连同其 DWM 阴影一起盖掉。**你实际测试的变化是 6 → 8，可见带宽只从 5px 变成 6px、墨量 +22%**——客观上是个很弱的变化，"看不出来"是合理的观感。

**③ 反馈面太小：** 实时预览框在 200% DPI 下是 184×240 物理像素，且只有它一处会跟随粗细变化，眼睛很难据此判断 1px 的差异。

### 4.3 修复方案

**第 1 步（必做，直接消除"完全不生效"）：让缩略图跟随真实粗细。**

```csharp
// StyleGallery.OnPaint
int thickness = _thickness;                       // 去掉 Math.Min(_thickness, 3)
int radius2   = _radius;                          // 去掉 Math.Min(_radius, 8)
int margin    = FrameStyles.MarginFor(_styles[i], thickness);   // 每个 tile 用自己的边距
...
FrameStyles.Draw(graphics, rectangle, color, text, thickness, radius2, margin);
```

若担心 12 个缩略图在大边距下"框贴着缩略图边、看不清楚"，更稳的做法是**保持缩略图视觉尺寸不变、按真实比例缩放整幅渲染**：先把 tile 按 `框尺寸 + 2×MarginFor(style, 8)` 的虚拟画布渲染到离屏 `Bitmap`，再等比缩放到 tile 大小。这样粗细 1..8 的**相对**差异在任何尺寸下都真实可见。

**第 2 步（推荐，让 6→8 也能一眼看出）：把整条环画到窗口外侧。**
把描边路径整体外移半个线宽，使全部线宽都落在窗口矩形之外：

```csharp
// FrameStyles.MarginFor：为描边预留整条线宽
public static int MarginFor(string style, int thickness) {
    int stroke = thickness;                       // 不再是 thickness/2+1
    return style switch {
        "Glow" => stroke + 10, "Aurora" => stroke + 10, "Neon" => stroke + 12,
        "Halo" => stroke + 14, "Dashed" => stroke + 7,  "Solid" => (int)(thickness * 1.8f) + 2,
        ... // 其余样式同理改为 stroke + 原光晕余量
    };
}
```

外框窗口矩形仍按新的 `MarginFor` 外扩（`FrameRectOf` 无需改动），描边路径则位于"可见边缘再向外半条线宽"处，粗细与可见带宽变成 **1:1 线性关系**（现在约 1:0.5，且被阴影吃掉一部分）。

**第 3 步：拖动期间始终把浮层置顶。**

```csharp
// DragEngine.Step / ShowOutline
_frame.RaiseAboveAll = true;      // 原为 inset：外扩模式下不置顶，向内半条线宽被目标窗口盖住
```

如果担心"置顶浮层遮住目标窗口内容"，可用 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`（已有）保证它不吃输入，仅在几何上与窗口重叠 1~2px。

**第 4 步：给预览加数值反馈。** 在预览框角落画 `粗细 8px`，或把 `_numFrameThick` 的值实时显示为 `当前 8px（范围 1–8）`，让用户知道参数已经被接收。

## 五、问题三：触发键激活后左键穿透点击

### 5.1 两条放行路径（均已用真实 Coordinator 复现）

**路径 A —— 阈值未到时的按下被放行，随后被"补发抬起"变成完整点击（真实使用中最常见）**

`Coordinator.OnMouseCore`（L1103–1123）：

```csharp
if (IsDownMessage(msg)) {
    if (_trigger.Active) { if (HandleButtonDown(num2, ms.pt)) return true; _passedDown[num2] = true; return false; }
    if (_trigger.Held) _heldDuringHold[num2] = true;   // ← 触发键已按住但未激活
    _passedDown[num2] = true;
    return false;                                       // ★ 按下原样放行给下层窗口
}
```

阈值到点后，L1089 的 `AdoptHeldButtonIfAny` 发现该键"已被按住"，于是 L1137 调 `HandleButtonDown`，而 L1322–1326 会因为 `_passedDown` 为真而**先补发一个抬起事件**：

```csharp
CancelTargetMouseMode(num);
if (_passedDown[idx]) { PostPairedButtonUp(num, idx, pt); _passedDown[idx] = false; }
```

`PostPairedButtonUp`（L1148）向该窗口 `PostMessageW(WM_LBUTTONUP)`。下层窗口先收到真实的按下、再收到这个抬起 → **一次完整点击成立**。

用合成钩子事件驱动桌面版真实 `Coordinator` 的复现结果（`evidence\3-click-pathA.txt`）：

```
① 触发键按下：被钩子吞掉=True  触发键已按住=True  已激活=False
② 阈值未到时的左键按下：被吞掉=False  → 放行给下层窗口=True
③ 阈值到：已激活=True
④ 补起拖动：拖动中=True  向该窗口补发的 WM_LBUTTONUP 次数=1
⑤ 左键抬起：被吞掉=True
```

这与你的运行日志完全对应：`holddrag.log` 中 `[诊断] 触发键激活时该鼠标键已被按住…→ 补起拖动` 共出现 **54 次**（最近一次 2026-10-16 12:45:29，键=0 坐标=2299,1009）。你的 `HoldMs = 200ms`，先按触发键再点左键时，几乎必然落在未激活的窗口里。

**路径 B —— 激活后解析不到目标窗口：按下与抬起都放行**

`HandleButtonUp`（L1416）在既没在拖动、也没有待吞抬起时返回 `false`，于是抬起也放行。复现结果（`evidence\3-click-pathB.txt`，用全屏置顶的本进程窗口模仿"设置页盖在桌面上"）：

```
目标解析：FindTarget=0（0 = 找不到可接管的窗口）
触发键：已激活=True
左键按下 被吞掉=False → 放行=True
左键抬起 被吞掉=False → 放行=True
```

**所以问题一和问题三是同一个根因的两种表现：**在设置页上，因为本进程窗口被排除 ⇒ 解析不到目标 ⇒ 按下、抬起全部穿到设置页；而设置页本身也因此永远无法被拖动。

### 5.2 修复方案

**核心原则：触发键一旦按住，鼠标键的事件流不允许再流向任何窗口；激活与否只影响"执行哪种动作"，不影响"是否吞掉事件"。**

**第 1 步：阈值期间缓冲按下，不要投递。**

```csharp
// New: 阈值窗口内记录的按下，尚未投递给任何窗口
private readonly bool[]  _bufferedDown  = new bool[3];
private readonly Native.POINT[] _bufferedPt = new Native.POINT[3];
private readonly bool[]  _bufferedMoved = new bool[3];

// OnMouseCore 的按下分支
if (IsDownMessage(msg)) {
    if (_trigger.Active) return HandleButtonDown(num2, ms.pt);      // 见第 2 步：内部保证吞掉
    if (_trigger.Held) {                                            // 触发键已按住：缓冲
        _bufferedDown[num2] = true;
        _bufferedPt[num2]   = ms.pt;
        _bufferedMoved[num2] = false;
        return true;                                                // ★ 吞掉，不投递
    }
    _passedDown[num2] = true;
    return false;                                                   // 未按触发键：正常点击
}
```

**第 2 步：激活时无条件吞掉已绑定动作的按键。**

```csharp
if (_trigger.Active) {
    bool swallowed = HandleButtonDown(num2, ms.pt);   // 解析不到目标 / Begin 失败 也返回 true
    return true;                                       // ★ 只要动作不是 "Nothing" 就绝不外泄
}
```

`HandleButtonDown` 内部约定改为：动作是 `"Nothing"` 时返回 `false`（保留"我不想接管这个键"的语义，事件照旧穿透）；其余情况一律返回 `true`，找不到目标就什么都不做。

**第 3 步：删除"补发抬起"，并用缓冲的按下补起拖动。**

```csharp
private void AdoptHeldButtonIfAny(Native.POINT pt)
{
    for (int i = 0; i <= 2; i++) {
        if (!IsButtonPhysicallyDown(i)) { _bufferedDown[i] = false; continue; }
        if (_bufferedDown[i]) {
            _bufferedDown[i] = false;
            // 早先的按下从未投递出去 → 不需要任何 WM_LBUTTONUP 补救
            if (HandleButtonDown(i, _bufferedPt[i]) /* 内部不再调 PostPairedButtonUp */)
                Log.Info("触发键激活时该键已被按住 → 补起拖动（按下从未投递）键=" + i);
        }
    }
}
```

**第 4 步：短按（未达阈值就松开触发键）时把缓冲的点击"还"给用户。**
阈值内按下 → 用户其实想要的是一次普通点击。在 `TriggerState` 处理触发键抬起、且 `Active == false` 时，用与现有 `ReplayMouseButton`（L223 一带）相同的手法 `SendInput` 补发"按下 + 抬起"（`dwExtraInfo = MagicExtraInfo` 以免被自己的钩子再次拦截），这样"轻点触发键 + 点击"的手感完全不变，也不会漏点击。

**第 5 步：清扫遗留机制。** `CancelTargetMouseMode`（`PostMessageW(WM_CANCELMODE)`）建议保留——它用于目标窗口在触发键按下前已进入拖选模态的情形，是无害的兼容处理；但 `PostPairedButtonUp` / `PhantomUpSentForTest` 这套"先放行再补救"的机制应当整体删除，它正是把"泄漏的按下"补成"完整点击"的那一步。

**第 6 步（可选）：** 增加 `AppConfig.SuppressClicksWhileTriggerHeld`（默认 true），给需要"按住触发键时仍能正常点击"的用户留开关。

### 6.3 第二轮追加修复：把「剩余风险」里可修的三项做掉

#### 6.3.1 拖动自身窗口时与设置页控件抢输入

**问题**：问题一放行本进程窗口后，若触发键恰好按住、指针又落在设置页的滑块/文本框/按钮上，程序会把整扇窗口拖走，而不是拖动滑块。三种情形都会发生：

| 情形 | 触发时机 | 原行为 |
|---|---|---|
| 已激活时按下 | `OnMouseCore` → `HandleButtonDown` | 抢走，改拖窗口 |
| 按住但未达阈值时按下 | `_trigger.Held & hasAction` 分支 | 缓冲按下，HoldMs 一到就被抢走 |
| 按下后阈值才到 | `AdoptHeldButtonIfAny` | 补起拖动，抢走 |

**修法**（改动 17–21）：新增 `WindowActions.IsPointOverOwnInteractiveControl(pt)`，判定链是 `WindowFromPoint → GA_ROOT → 根窗口属于本进程且是合法自有窗口（非浮层/探针） → 命中窗口的类名可交互`。可交互类名是一张白名单（滑块、编辑框、按钮、下拉框、上下调节、滚动条、进度条、列表/树/标签页/状态栏/工具栏/日历/日期选择/IP 控件 + `RichEdit*`）。

三处路径分别在判定为真时改为**放行**：

```csharp
// HandleButtonDown：接管拖动之前先让路给控件
if (Actions.IsDragAction(text) && WindowActions.IsPointOverOwnInteractiveControl(pt)) {
    _passedDown[idx] = true; _bufferedDown[idx] = false;
    _heldDuringHold[idx] = false; _swallowUp[idx] = false;
    return false;                                   // 按下与抬起都还给控件
}

// OnMouseCore 的阈值缓冲分支：不缓冲，直接放行
if (WindowActions.IsPointOverOwnInteractiveControl(ms.pt)) { _passedDown[num2] = true; return false; }

// AdoptHeldButtonIfAny：已激活也不抢；只把"从未投递出去"的那次按下补还给控件
if (WindowActions.IsPointOverOwnInteractiveControl(pt)) { /* 见 6.1 第 21 项 */ return; }
```

**一个必须踩的坑**：WinForms 会把系统控件类名包装成 `WindowsForms10.<基础类名>.app.0.xxxxx_r3_ad1`。第一版只比对 `msctls_trackbar32`，T86 用例直接报红（实测类名 `WindowsForms10.msctls_trackbar32.app.0.3279090_r3_ad1`）。因此 `IsInteractiveClassName` 会先剥掉 `WindowsForms10.` 前缀、截到下一个 `.` 之前，再比对基础类名。

**边界**：容器类（`Panel` / `GroupBox`）与静态文本（`Label`）**不在**白名单里，标题栏、边框、空白客户区也不在——所以「按住触发键把设置页整体拖走」照旧可用，只是不会再去抢控件。

#### 6.3.2 自检 T80 的偶发失败

**根因**：`LaunchExternalWindow()` 用 `FindWindowByTitle("HoldDrag 外部测试窗口")` 找宿主，而宿主的标题是**常量**。自检被中断（Ctrl+C / 崩溃）会留下孤儿宿主，下一轮就会：

1. 命中**上一轮的旧窗口**（而不是这次新拉起的那个）；
2. 收尾时 `Process.GetProcessById(PidOfWindow(num)).Kill()` 杀掉旧宿主，**同时漏掉自己刚拉起的那个**；
3. 于是下一轮又有两个残留 → 失败自我复制。

**修法**（改动 22）：三件事一起做——

1. `RunWindowHost()` 把窗口标题改成 `HoldDrag 外部测试窗口 #<本进程PID>`，每轮唯一；
2. `LaunchExternalWindow()` 启动前先 `KillStaleWindowHosts()` 清掉同前缀的孤儿（绝不包含自身），再按「标题前缀 + 本次 PID」精确定位（`FindWindowByTitleForPid`，失败才回退精确标题）；
3. 收尾统一走 `KillWindowHostProcess(hwnd)`，只结束该窗口所属进程，并显式拒绝结束自身 PID。

**验证**：连续 3 次自检，T80 三次全绿，三次拉起的宿主句柄各不相同（`AA1458` / `AA009E` / `BE11FE`），说明每轮都是新宿主且都被正确清理。

## 八、实施决策与剩余风险

### 8.1 替你做的决策

1. **`RaiseAboveAll` 改为恒真**，即外框在拖动/悬停期间始终置顶。理由是浮层带 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`，不吃输入；而原来的「外扩模式下不置顶」正是让向内半条线宽被目标窗口连同 DWM 阴影一起盖住的原因。若你更在意「不要盖住别的窗口的悬浮提示」，这是本次唯一需要你确认的语义变更。
2. **`MarginFor` 改为 `ceil(StrokeFor) + 光晕余量`**，外框窗口因此比原来每边多出约 `thickness/2` 像素（Dashed t=8：12 → 15 px）。副作用是贴屏时更容易走进 `FillsScreen` 的「内缩」分支；自检里的贴边用例已复跑通过。
3. **没有新增「允许拖动自身窗口」的 UI 开关**。原因：`FindTarget` 放行本进程窗口后**仍会走 `IsBlacklisted`**，而黑名单同时匹配窗口类名、标题和**进程名**——把 `HoldDrag` 填进「黑名单」即可屏蔽自身窗口，退出通道已经存在；而在 `groupBox4` 里插入复选框需要重排 5 个同级控件的 Y 坐标，收益不抵布局风险。配置项 `AllowDragOwnWindows` 仍然保留（默认 `true`），可直接改 `config.json` 关闭。
4. **可交互控件优先，而不是「只在非客户区才接管」**。第二轮修复的取舍是：指针落在自有窗口的**可交互控件**上就一律让路，其余位置（标题栏、边框、空白客户区）照旧可拖。换成「仅在非客户区接管」也能避开滑块，但设置页客户区里大片空白就都拖不动了，得不偿失。
5. **T80 用「唯一标题 + 精确 Kill」而不是「每次先把同名宿主全杀光」**。后者在同时跑多个自检时会把别人的宿主一并杀掉；前者既清残留又只动自己拉起的那一个。

### 8.2 剩余风险

1. **`Solid` 样式的外框仍比原版每边多 0～5 px**（t=8：10 → 15 px）。这个量在数学上已经压不下去：`Solid` 的笔画宽是 `1.8t`，而外扩量必须 ≥ 笔画宽，否则 `Draw` 里内缩 `stroke/2` 之后描边外缘会落到浮层边界外被裁掉——那正是原来「粗细改了看不出」的成因之一。若你希望外框尺寸与旧版**完全一致**，把 `StrokeFor` 里 `Solid` 的 1.8 倍系数改成 1.0 即可（一行），代价是放弃「Solid 比其它样式更粗」这一原设计意图。
2. **可交互控件白名单是枚举式的**。已覆盖 WinForms 常见控件（滑块 / 编辑框 / 按钮 / 下拉框 / 上下调节 / 滚动条 / 进度条 / 列表 / 树 / 标签页 / 状态栏 / 工具栏 / 日历 / 日期 / IP）与 `RichEdit*`。若你的工程里有**自绘控件**（类名 `WindowsForms10.Window.*`）且需要鼠标拖选文本，它会被当作「可拖区域」而不是控件；此时把该基础类名加进 `WindowActions.InteractiveClasses` 即可。

## 十、第三轮修复：按住触发键时同步按左键，「外框出来了但左键毫无反应」

### 10.1 你的报障

> 「我同时按 enter 和左键，虽然会触发功能，因为该窗口的外框已经出现了，但实际上左键什么功能都没有，也不能够顺利的通过左键来移动窗口」

关键信息有三条，缺一不可：**外框出来了**（说明触发键已过阈值、激活链路正常）、**左键什么都做不了**（说明按下被处理成了别的东西）、**移动不了窗口**（说明拖动会话压根没建立）。三者叠加，把范围锁死在「激活之后、拖动建立之前」这一段。

### 10.2 根因（两处，互相叠加）

#### 10.2.1 主因：阈值期间被缓冲的按下，要等到「激活后的第一次鼠标移动」才被收养

第一轮修问题三时，为了让「触发键激活后左键不再穿透点击」，引入了**缓冲**语义：触发键按住但还没到 `HoldMs` 阈值的那段时间里，任何左键按下都**不投递给下层窗口**，先记进 `_bufferedDown[]`；等激活后再由 `AdoptHeldButtonIfAny` 把它「收养」成一次拖动。

问题出在**收养的时机**：`AdoptHeldButtonIfAny` 只在 `OnMouse` 的**移动**分支里被调用。于是「同时按 Enter 和左键」这个动作会踩中一个必现的坑：

```
t0  按下 Enter          → 触发键进入"按住中"，HoldMs 计时开始
t1  按下左键            → 落在阈值窗口内 → 被缓冲，下层窗口什么都没收到
t2  HoldMs 到点          → 激活：外框亮起（你看到的现象）
t3  手指还按着左键，但没动 → 没有任何"移动"事件 → 收养从未被调用
                            → _drag.IsDragging 一直是 false
                            → 左键"什么功能都没有"，窗口当然也拖不动
```

而绝大多数人的操作习惯是**按下左键的同时或之后立刻开始移动**，于是 t3 很快被跨过，问题被掩盖——所以这条缺陷只在「按下后先不动」时暴露。

**修复**：新增 `Coordinator.AdoptBufferedButtonsNow(pt)`，在 `OnTriggerActivated` 激活的**那一瞬间**就执行收养，不再依赖后续鼠标移动。

```csharp
// Coordinator.OnTriggerActivated(pt)（L921 附近）—— 第三轮改为：
CancelTargetMouseMode(num);
AdoptBufferedButtonsNow(lpPoint);          // ★ 激活瞬间就补起，不再等"下一次鼠标移动"
if (!_drag.IsDragging)
{
    _drag.ShowHoverFrame(lpPoint);         // 已经在拖了就别再画悬停框
}
```

`AdoptBufferedButtonsNow` 的取舍（写在方法注释里，供后续维护）：

- **只收养 `_bufferedDown`，绝不动 `_passedDown`**。被缓冲的按下从头到尾没离开过本进程，目标窗口根本没收到 `WM_*BUTTONDOWN`，所以不存在「用户其实想在那里选文字/拖选区」的可能；而 `_passedDown` 的按下目标窗口**实收了**，必须由用户移动来表明意图，否则「先选文字、再按触发键」会被误判成拖窗口。
- **收养前先查 `IsButtonPhysicallyDown`**：用户在阈值到点的同一刻松手时要顺手清账（`_bufferedDown` / `_heldDuringHold` 一起清），不留残留。
- **收养前先查 `IsPointOverOwnInteractiveControl(pt)`**：指针停在自有窗口的滑块/编辑框上时，把按下用 `ReplayBufferedClick(i, keepDown: true)` **还给控件**，不接管。
- 补起拖动时**起点取当前光标**（不是缓冲点），否则补起那一帧窗口会跳变——自检里有 `Eq(lpAdopt.Left - lpRect.Left, 0)` 两条专门盯这个。

#### 10.2.2 次因：`GroupBox` 的窗口类是 `BUTTON`，被白名单误判成「可交互控件」

第二轮的修复是「指针落在自有窗口的**可交互控件**上就一律让路」。白名单 `WindowActions.InteractiveClasses` 里有 `"Button"`——**而 WinForms 的 `GroupBox` 正是用 `BUTTON` 窗口类实现的**（靠 `BS_GROUPBOX(0x7)` 样式位区分于真按钮）。

后果：设置页里成片的 `GroupBox` 覆盖了大部分客户区，指针停在这些区域时 `IsPointOverOwnInteractiveControl` 返回 **true** → 按下被放行给 `GroupBox` → `GroupBox` 是容器、不吃鼠标 → 「左键点了没有任何反应」，窗口也拖不走。**这正好是你描述的现象**，而且它和 10.2.1 的主因会叠加：即使收养时机修对了，指针若落在分组框上，收养阶段同样会走「还给控件」分支。

**修复**：判定函数从「只看类名」改为**必须传句柄**，并在类名匹配到 `Button` 之后再看样式位：

```csharp
/// <summary>该窗口句柄是否为"可交互控件"。必须传句柄：单看类名分不出 GroupBox 与 Button。</summary>
internal static bool IsInteractiveControl(nint h)
{
    string cls = Native.GetClassName(h);
    if (string.IsNullOrEmpty(cls)) return false;
    // WinForms 会把系统控件类名包成 WindowsForms10.<基础类名>.app.<版本>_r<n>_ad<n>，
    // 实测滑块 = WindowsForms10.msctls_trackbar32.app.0.3279090_r3_ad1
    const string WinFormsPrefix = "WindowsForms10.";
    if (cls.StartsWith(WinFormsPrefix, StringComparison.OrdinalIgnoreCase))
    {
        int i = cls.IndexOf('.', WinFormsPrefix.Length);
        if (i <= WinFormsPrefix.Length) return false;
        cls = cls.Substring(WinFormsPrefix.Length, i - WinFormsPrefix.Length);
    }
    if (!MatchesInteractiveName(cls)) return false;
    // GroupBox 也是 BUTTON 类，只有 BS_GROUPBOX(0x7) 能把它和真按钮区分开。
    // GroupBox 是容器、不吃鼠标拖动 —— 不排除它，设置页成片的分组区会把"拖窗口"整个吃掉。
    return !(string.Equals(cls, "Button", StringComparison.OrdinalIgnoreCase)
             && (Native.GetWindowLong(h, -16) & 0xF) == 0x7L);
}
```

### 10.4 顺带修掉两个「环境敏感」的假红用例（不改产品语义）

#### 10.4.1 T69「40% 外框必须明显比 100% 淡」——被桌面壁纸底色骗了

原判定：`num3 < num2 * 0.6`（40% 时的屏幕青色度必须小于 100% 时的 0.6 倍）。

问题：外框是**半透明**浮层，屏幕读数必然是 `alpha × 外框色 + (1-alpha) × 背景`。这个固定阈值等价于假设「背景远比外框暗」。本机壁纸恰好是深青（实测采样带像素 `RGB(4,70,91)` → 青色度 23），于是：

| 采样带背景青色度 `bg` | 理论值 `0.4×60 + 0.6×bg` | 实测 40% 读数 | 旧判定 |
|---|---|---|---|
| 8 | 29 | 29 | 通过 |
| 23 | 38 | 36 | **假红** |
| 37 | 46 | 44（另一次 46） | **假红** |

三次读数 29 / 36 / 46 与公式逐一对上，说明**产品渲染完全正确**，是判定式写错了。

```csharp
int num4 = (int)(0.4 * num2 + 0.6 * bg) + 4;

Check(num2 - num3 >= (num2 - bg) / 2, "★ 40% 至少削掉一半「外框−背景」对比度（整层等比变淡）", ...);
```

## 十一、真实输入链路端到端验收（补上此前所有验证都缺的那一环）

### 11.1 为什么必须补这一环

前面所有的自检都是**进程内直接调用** `Coordinator.OnMouse(...)` / `Trigger.SimulateKeyDown()`，**绕过了 `HookEngine` 与真实低级钩子链路**。你的报障是手动按键产生的，走的是完整钩子路径——两者不是一回事：进程内直调只能证明「逻辑写对了」，不能证明**真实输入下确实生效**。你那句「这一版本你好像没有给我真正的修复」，正是这一环缺失的合理质疑。

为此新增验收工具 `work\inpute2e\InputE2E.cs`：
- 用 `SendInput` 注入**真实**输入（`dwExtraInfo = 0`，不是 HoldDrag 自签的 `1215261796`）；
- 目标窗口为验收进程自己的窗体（对 HoldDrag 而言即外部进程窗口）；
- 逐步注入鼠标移动，**逐帧记录目标窗口的实际位移**，直接看出「跟不跟手」。

> ⚠️ 工具自身踩过一个坑，值得记下来：**`SetCursorPos` 不会产生鼠标输入事件**，低级钩子看不到它。第一版工具用 `SetCursorPos` 移动光标，结果两版读数全是 `+0,+0`（假阴性）。必须改用 `SendInput(MOUSEEVENTF_MOVE)`。

### 11.4 一个必须如实说明的边界：落键次序

人手说「同时按」，实际有两种落键次序，结论不同：

## 十二、第六轮修复：「按下左键就立刻移动 → 窗口拖不动」的真凶是 GetAsyncKeyState 漏报

### 12.1 用户给的决定性对照

> 「我按 enter 然后快速的按下左键，这时候窗口的外框显示被样式包围，但确实这时候鼠标怎么动这个窗口都移动不了……
> 如果我按住左键过一段时间再移动，这时候是能够顺利移动的，右键也能够顺利发挥功能。」

这两种操作唯一的差别是：**触发键到 200ms 阈值之前，鼠标有没有已经在动。**

### 12.2 把它变成机器时序（`InputE2E` 新增 `fastmove` 等模式）

`work/inpute2e/InputE2E.cs` 用 `SendInput`（`dwExtraInfo = 0`，与真人输入等价；`SetCursorPos` 不算——低级钩子看不到它）注入真实输入，逐帧读目标窗口的 `GetWindowRect`：

| mode | 时序 | 修复前 | 修复后 |
|---|---|---|---|
| `simult` | Enter → 30ms → 左键 → 等 700ms → 移动 | +150,+60 | +150,+60 |
| `sequ` | Enter → 420ms（已激活）→ 左键 → 移动 | +150,+60 | +150,+60 |
| `taphold` | Enter → 点一下左键 → 再按住左键 → 移动 | +150,+60 | +150,+60 |
| **`fastmove`** | Enter → 20ms → 左键 → **不等待，立刻逐帧移动** | **+0,+0** ✘ | **+200,+80** ✔ |
| `tap` | Enter → 点一下左键 → 移动 | +0,+0 | +0,+0（点按后已松手，按住语义下本就不该拖） |

`fastmove` 的逐帧轨迹（修复后）：

```

TRACE mode=fastmove step=move5  cur=975,580  期望=+125,+50 win=525,310 实际=+25,+10   ← 激活，开始接管
```

从激活那一刻起**每一步都严格 +25,+10**，即 1:1 跟手。前面 4 步落在 200ms 阈值之内 —— 触发键还没激活，任何实现都不可能动，属设计边界。

### 12.3 真凶：`IsButtonPhysicallyDown()`（`GetAsyncKeyState`）在本进程会漏报

抓到现行的一行现场日志（`%AppData%\HoldDrag\holddrag.log`，21:07:47）：

```
21:07:47.473 [诊断] 鼠标键按下 键=0 触发[按住=True 激活=False] 缓冲=False … 坐标=850,530
21:07:47.635 [诊断] 激活瞬间清点缓冲 缓冲[True,False,False] 阈值期按住[True,False,False]
                                 已放行[False,False,False] 物理按下[False,False,False] 坐标=950,570
21:07:48.073 [诊断] 鼠标键抬起 键=0 触发[按住=True 激活=True] … 拖动中=False 坐标=1000,590
```

- 左键**确实按着**：47.473 收到按下，48.073 才收到抬起，中间 600ms 一直按住；
- 缓冲账里也**确实有这条按下**（`缓冲[True,…]`）；
- 可 `GetAsyncKeyState(VK_LBUTTON)` 报 **False**。

老代码在激活瞬间的第 2 道关卡是：

```csharp
if (!IsButtonPhysicallyDown(i))   // 系统的这句"没按着"
{
    _bufferedDown[i] = false;      // → 把刚收到、还热乎的缓冲按下整条丢掉
    _heldDuringHold[i] = false;
    continue;
}
```

于是：**缓冲按下被当成"用户已松手"丢掉 → 激活后每一次鼠标移动又被 `AdoptHeldButtonIfAny` 里同一个查询挡回去 → 拖动永远建不起来**；而外框由 `ShowHoverFrame` 照常画出。这就是「外框被样式包围，但鼠标怎么动窗口都移动不了」。

为什么"按住左键过一会儿再移动"就正常：那种时序里左键是在**激活之后**才按下的，走的是一条完全不同的分支（`HandleButtonDown` 直达），根本不经过这道被污染的关卡。

### 12.4 修复思路：判据只用「钩子事件账本」，再也不信这个查询

低级鼠标钩子能**直接看到**每一次鼠标键按下/抬起。账本语义精确且自洽：
**收到按下 + 尚未收到配对的抬起 ⟺ 键还按着**；抬起分支（`OnMouseCore` 的 up 分支）会把三本账全部清零，所以账本不会长期失真。
`GetAsyncKeyState` 在本进程被实测证明会漏报，作为判据只会把好账当坏账。

改动（`work/fixed/HoldDrag.cs`，累计补丁 50 hunk）：

**① `AdoptBufferedButtonsNow`（激活瞬间）**：删掉 `if (!IsButtonPhysicallyDown(i)) { 清账; continue; }` 这道关卡。缓冲账里有按下就直接收养。
**② `AdoptHeldButtonIfAny`（激活后随光标移动接管）**：判据从"物理键状态 + 三本账"改成**只看三本账**（`_bufferedDown || _heldDuringHold || _passedDown` 任一为真即接管）。自有窗口可交互控件上的让路逻辑原样保留。
**③ `FlushBufferedClicks`（触发键短按补还点击）**：`keepDown` 也改成按账本判定（账本还在 ⟺ 用户仍按住），补"按下"而不补"抬起"，用户真实抬起稍后原样送达 —— 拖滑块/选文本的按住过程不再被打断。
**④ 兜底**：`OnTriggerDeactivated` 里若仍在拖动，立刻 `_drag.End()`。松开触发键一定收手（「鼠标抬起」这条事件同样可能落在钩子重装的缝隙里丢掉）。
**⑤ 诊断留痕（长期保留，只在触发键按住/激活期间写，量极小）**：

### 12.8 一个需要你确认的边界（`tap` 那一档）

如果你实际的习惯是**"点一下左键就松开、然后再移动鼠标"**（而不是一直按着），那么按当前语义**不会**拖动 —— 因为松开左键之后没有任何东西"按着"这个窗口。

这属于产品语义选择（"按住才拖" vs "点一下抓住 / 再点一下放下"）。你原来的描述里说的是「按住左键过一段时间再移动是能顺利移动的」，听起来是**按住**的习惯，所以本轮按"按住才拖"实现。**如果你的习惯其实是"点一下抓住"，回我一句，我把"点一下左键 = 抓住窗口、随光标移动，再点一下或松开触发键 = 放下"这个模式加上去。**
