### 用户提的三条

2. **长按到阈值、还没按鼠标键时，光标底下那扇窗就该亮起外框**

### 关键根因（务必记住）

**外框残留 = 跨线程竞态，不是"忘了隐藏"。**
`DragEngine.Step()`（工作线程）的收尾顺序是：校验会话代次 → `SetWindowPos` → 显框。
`SetWindowPos` 在目标窗口忙时会阻塞几十毫秒，这段时间里钩子线程已经走完 `End()` 把外框隐藏了；
等工作线程出来，它手里那份"会话仍有效"的判定已过期，却照着它又把外框画了一次，之后再没人关。
→ 修法 `DragEngine.TryShowFrame()`：**判定与投递必须在同一把锁里完成**。
  只要有一瞬是在锁外做的判定，收尾线程就能钻进空隙把外框关掉、我们却还拿着旧结论画出来。
  另加 `volatile bool _frameWanted` 做第二道闸，`Cleanup()` 里先关闸再隐藏。

**圆角"又直又尖" = `CreateRoundRectRgn` 没有抗锯齿。**
GDI 区域是硬边（1bit 掩码），圆角在屏幕上就是一级级锯齿。
→ 改成 32bpp 位图 + GDI+ `SmoothingMode.AntiAlias` 描边 + `UpdateLayeredWindow` 提交。
  顺带解决了残影（位置/尺寸/像素原子提交）。**以后凡是"圆角要好看"都别用 GDI 区域。**

### ★ 诊断进程不退出（这次彻底搞清了）

`--selftest` / `--stress` 报告写完、进程却一直挂着，之前挂"3 秒后自杀"的兜底线程**没用**。
根因：**`Environment.Exit` 在真正 `ExitProcess` 之前会挂起其它线程**，兜底线程根本等不到调度；
而它自己要 flush 控制台缓冲、跑 ProcessExit 处理器，这条路径上任何一处卡住进程就出不去。
→ 改成直接 `Native.TerminateProcess(GetCurrentProcess(), (uint)code)`，退出码语义也保住了。
实测：退出码 0、无残留进程。
**正常启动路径（--smoke 验证过）本来就能干净退出**，日志有"冒烟测试完成，自动退出 → 退出"。

## HoldDrag v3.1 —— 修复缩放跟手性与拖动残影/抖动

用户继续反馈：
1. 右键缩放"没有那么跟手"。
2. 仍有残留拖影。
3. 左键移动时窗口内容（字）在抖。

### 根因与修法

**缩放不够跟手 = `RESIZEFLAGS` 没加 `SWP_ASYNCWINDOWPOS`。**
`SetWindowPos` 同步调用时，目标窗口一卡工作线程就被拖住，下一帧进不来，鼠标已经走了、窗口还在原地哆嗦。
→ 缩放与平移统一走异步：`RESIZEFLAGS` / `MOVETHICKBORDERS` / `MOVEASYNC` 全部带 `SWP_ASYNCWINDOWPOS`。

**缩放残影 = 缺 `SWP_NOCOPYBITS`。**
系统默认会把旧窗口像素按新矩形复制，缩放时旧内容被拉伸/复制到新尺寸，松开鼠标后还会残留一帧。
→ `RESIZEFLAGS` 加 `SWP_NOCOPYBITS`；异步之后补 `WM_SYNCPAINT`，让目标窗口立刻重绘，避免堵在 `WM_SIZE` 队列里滑过去。

**平移时字在抖 = 平移也加了 `SWP_NOCOPYBITS`。**
NOCOPYBITS 会强迫窗口逐帧全刷，普通程序重绘跟不上就抖。
→ 平移（`MOVETHICKBORDERS` / `MOVEASYNC`）**不加** `SWP_NOCOPYBITS`，让 DWM 直接整窗复制到新位置；
  同时纯平移不再发 `WM_SYNCPAINT`，避免逐帧同步重绘。

### 改动文件

- `Native.cs`：新增 `SWP_NOCOPYBITS` 常量；重定义 `RESIZEFLAGS`、`MOVETHICKBORDERS`、`MOVEASYNC`。
- `WindowActions.cs`：更新 `SetDragRect` 注释；`WM_SYNCPAINT` 改为只在带 `SWP_NOCOPYBITS` 时发送。
- `README.md`：更新标志位策略说明和压力测试数据。

### 验证结果（v3.1 交付）

- 构建：`dotnet build -c Release -o ../_build5/pub`，**0 警告 0 错误**。
- `--selftest`：**191 项，通过 191，失败 0，退出码 0**。
- `--stress`：
  - 预热：句柄=575  GDI=117  USER=71  私有=49MB  工作集=100MB
  - 80  次：句柄=654  GDI=117  USER=71  私有=51MB  工作集=105MB
  - 160 次：句柄=655  GDI=119  USER=71  私有=67MB  工作集=130MB
  - 640 次：句柄=655  GDI=119  USER=71  私有=67MB  工作集=130MB
  - GDI +2、USER +0、句柄 +80 后走平、私有内存 +18MB 后走平 → 未发现泄漏，退出码 0。

## HoldDrag v3.2 —— 真正的病根：拖动期的分层外框每帧整图上传

⚠️ **v3.1 方向就错了**：用户反馈"跟原来差不多"。深挖后确认真正的病根不是 SetWindowPos 标志位
（v3.1 的 ASYNC/NOCOPYBITS 调整只是让窗口写得更规矩），而是**拖动进行中的激活外框本身就是个性能灾难**：

- ActivationFrame 是分层位图浮层，每动一帧都要 `UpdateLayeredWindow` **重新上传整张窗口大小的位图**
  （窗口多大图就多大，160Hz 下一张 1600x900 的图每秒上传 ~900MB），缩放时还要每帧重建 GDI+ 位图；
- 更糟的是它的更新要走 `PostMessage → UI 线程`，和工作线程的 `SetWindowPos` **不同拍**，
  窗口已经走了、环还在后面追 → 用户看到的"拖影/残影"其实是**外框自己在拖尾**；
- 这条消息管道每帧还要把 UI 线程从设置窗口等事情里拽出来，反过来拖慢整个合成。

### 修法（v3.2）

1. **新增 `DragRingFrame`（区域环）**：`SetWindowRgn` 抠出圆角环 + 纯色填充。
   平移 = 一次 SetWindowPos（copybits 零重绘）；缩放 = 一次 SetWindowPos + 一次 SetWindowRgn。
   由工作线程**同步直写**（`SWP_NOSENDCHANGING` 防跨线程阻塞），和 SetWindowPos 同一拍。
2. **双框分工**：拖动进行中 = 区域环（快、跟手）；松手/悬停 = 抗锯齿分层框（好看、静止）。
   `DragEngine.Begin` 收分层框亮环，松手后 `Coordinator` 的悬停逻辑自动换回分层框。
3. **平移标志回退 AltSnap 原版**（同步 MOVETHICKBORDERS / 异步 MOVEASYNC，不加 NOCOPYBITS）。
   `WM_SYNCPAINT` 只在缩放路径下发且超时从 120ms 降到 8ms（提示而已，等 120ms 会被慢窗口每帧堵死）。

### 环境坑（新增）

- **TickTick.exe 的 GridWidget 常驻置顶小组件**会盖住屏幕中心，把 T27 全屏用例的
  WindowFromPoint 命中抢走 → 假失败。已把 T27 改硬：命中其它窗口时打印类名并跳过正向断言，
  只有"一个都没命中"才算真失败。
- `dotnet build` 产出的 HoldDrag.exe 只是 apphost 壳（~200KB），真身在旁边的 dll；
  **交付必须 `dotnet publish`**（单文件 387KB）。
- 沙箱杀 schtasks 的特性仍在，--smoke 跑不了，只能用户真机验证。

### 验证结果（v3.2 交付）

- `dotnet publish -c Release`：0 警告 0 错误，单文件 exe 387,346 字节。
- `--selftest`：**200 项，通过 200，失败 0，退出码 0**（新增 T32：拖动中环/框分工 + 松手切换回归）。
- `--stress`：GDI 121→122(+1)、USER +0、句柄 +80 后走平、私有内存 65→67MB 后走平 → 未发现泄漏。
- `--smoke`：环境限制跑不了（schtasks 被沙箱杀），待用户真机验证。

## HoldDrag v3.3 —— 主题不生效 / 动作后外框消失 / 设置窗口可调尺寸

用户新提四条（本轮）：
1. **主题（外框颜色/样式/粗细/圆角）保存后没真正应用。**
2. **设置窗口长宽不可调。**
3. **按住 Enter 触发后，用左键或右键执行动作，包围窗口的外框会消失** —— 要求继续保持。
4. 尽可能提高性能、优化残影与抖动。

### 三条根因（都是这一轮才定位清楚的）

**①「外框消失」= `HandleButtonDown` 的非拖动分支少了一次重新亮框。**
拖动类动作（左键拖动 / 右键缩放）走 `Begin`/`End`，`End` 之后 `HandleButtonUp` 会重新
`ShowHoverFrame`，所以它本来是对的。但**非拖动**的一次性动作有三条独立路径全都漏了：
- `WindowActions.Apply`（中键=最大化 / 任意键=居中/置顶/最小化…）
- 双击左键 → `MaximizeRestore`
- 双击右键 → `ApplyZoneDoubleClick`

这三条原先只设 `_swallowUp[idx]=true` 就返回，**没人把框重新亮回来**；松开鼠标后光标不动，
悬停刷新也不会触发 → 外框一直隐着。
→ 新增 `Coordinator.RefreshHoverAfterAction(pt)`，在这三条路径后调用；
  并**先 `_drag.InvalidateHover()` 再 ShowHoverFrame** —— 因为这类动作往往刚改过窗口矩形
  （最大化最典型），沿用旧的"还是同一扇窗"缓存会把框留在旧位置。

**②「主题不生效」= 只重建了位图，没调 `UpdateLayeredWindow`。**
外框是分层窗口，像素靠 `UpdateLayeredWindow` 提交。`MarkContentDirty()` 旧实现只
`Rebuild()`（重建位图 + GDI 句柄），**没有接着 Push**。新外观静静躺在内存里，
要等下一次 `SetRect`（鼠标移开、光标换窗）才画出来 → 用户看到"改了没反应"。
→ 新增 `WM_RETHEME` 消息 + `OverlayWindow.RequestRetheme()` / `OnRetheme()`：
  外观变更投递回 UI 线程（创建浮层的线程），**重画 + 用 `_lastPlacedX/Y` 原地重推**。
  另在 `Coordinator.OnConfigChanged()` 里加 `_drag.RefreshOverlayTheme()`，
  保证点「保存并生效」是字面意义上的立刻生效。
  `DragRingFrame.ApplyTheme` 也补了 `InvalidateRect`（换刷子不会自动重绘）。

**③「设置窗口不可调尺寸」= `FixedSingle` + 绝对定位。**
→ 改 `Sizable` + `MaximizeBox=true` + `MinimumSize(578,420)`；给六个 GroupBox 全部加
  `Top|Left|Right` 锚定（**只改 BorderStyle 不加锚定＝拉宽只多出空白**），
  右列控件（预览框、缩放角区、双击右键、提权按钮）锚 `Top|Right`，
  说明性 Label / 黑名单 TextBox 锚 `Left|Right`。
  新增 `SettingsWidth/SettingsHeight` 配置项持久化窗口尺寸（0=默认，Normalize 夹到 578..2400 / 420..2400），
  用 `RestoreBounds` 记录（最大化时记还原尺寸）。点"取消"不落盘。

### 顺手做的性能优化

- `OverlayWindow.SetRect`：加"和待处理/已落地矩形完全相同就直接返回"，
  省掉安静时的 UI 线程唤醒（拖动起步几毫秒、悬停静止时都是重复矩形）。
- `ShowHoverFrame`：同一扇窗的分支里加一次 `GetWindowRect` 比较，
  窗口没动就真的什么都不做；**窗口被动过（别的程序挪它、我们执行完一次性动作）
  就重贴** —— 这同时修掉了"框脱离窗口停在旧位置"。
- `Coordinator`：`HandleButtonUp` / `RefreshHoverAfterAction` 改用钩子事件自带的 `ms.pt`，
  不再多调 `GetCursorPos`（钩子回调里能省一次系统调用就省）。

### 新增自检（220 项）

- **T33** 外框消失回归：中键一次性动作 + 双击左键最大化，两条路径做完后外框仍可见，
  松开触发键才消失。（★ 这条第一版因为最大化有 ~200ms 系统动画、只 Settle() 80ms 读矩形而假失败，
  加 `SettleLong()` 500ms 后通过。）
- **T34** 设置尺寸回归：`VerifyResizable` + `VerifyAnchors`（六个分组必须带 Left|Right），
  以及 SettingsWidth/Height 的 Normalize 夹取。
- **T35** 主题生效回归：**`GetDC(NULL) + GetPixel` 直接读屏幕像素**，
  断言换成朱红之后描边位置的颜色立刻接近朱红。这是唯一能证明"真的画到屏幕上了"的办法。
  为此给 `Native.cs` 补了 `GetPixel` P/Invoke。

## 立个新章节：两列布局「断行 + 同行容差」模型（v3.4）

用户上一轮明确说过「拉宽要真的利用宽度，不要搞稀奇古怪的东西」，
本轮把两列模式下的**内容挤压/截断/重叠**彻底做干净了。

### 三个真 bug（都不是"差不多就行"，是实打实的渲染错误）

1. **复选框文字被切**：`TextNeed()` 给 CheckBox 用的是 `TextRenderer.MeasureText + 24`，
   实测**恒定少 10~17px**，正好切掉最后一个字
   （"…就立即生效"缺尾、"九宫格吸附"缺"附"）。
   - 实测（125% DPI / 微软雅黑 9pt）：
     | 文字 | TextRenderer | +24 | PreferredSize | 差 |
     |---|---|---|---|---|
     | 需要长按触发…生效 | 494 | 518 | **535** | +17 |
     | 双击右键 = 九宫格吸附 | 262 | 286 | **296** | +10 |
     | 开始拖动时自动…最前 | 350 | 374 | **386** | +12 |
   - **纠正一个记错的认知**：`CheckBox.PreferredSize` 在 `AutoSize=false` 下**是有效的**
     （走 `ButtonBase.GetPreferredSizeCore`，含勾选框+内边距+文字）。
     我上一轮注释里写"它返回当前尺寸"是错的（那是 `Label` 的行为）。
     凡是要量 CheckBox 宽度，一律用 `PreferredSize`，别自己猜常数。

2. **并排复选框挤不下时不会换行** → 新增 `ComputeRowWraps()` + `ApplyRowWraps()`，
   放不下就**断行、独占整行**（等价 HTML `flex-wrap`）。
   判定必须用**实际渲染宽度**（`c.Width`），不能用 `BaseWidth` ——
   Grow 类复选框 BaseWidth=240 但实际会拉到 318，拿 240 判断永远"放得下"。

3. **`LeftBarrier` / `PropagatePush` 混用"基准坐标"和"实时坐标"** —— 本轮最大的坑。
   - `LeftBarrier` 用 `other.BaseLeft`（基准）但 `c.Top`（实时）判同行；
   - 断行的多轮试探里 Y 会来回变，"填窗口标题"那行实时 Top 还是 0 时
     被误判成和 T=84 的"缩放角区"同行 → 它的右边界 518 成了"左边的墙"
     → "缩放角区"被顶到 526、压成 20px。
   - **教训：布局代码里要么全用基准、要么全用实时，绝不能一半一半。**

### 同行判定的正确口径（统一到三处：LeftBarrier / PropagatePush / ComputeRowWraps）

不能用矩形相交。设计稿行距 29px（BaseTop 81 → 110），而 125% DPI 下控件本身 30+ 高，
矩形天然"咬"进去几像素，会把**下一行**误判成同行。正确做法是**重叠过半**：

```csharp
int ov = Math.Min(bottom, oBottom) - Math.Max(top, oTop);
if (ov <= 0) continue;
if (ov * 2 < Math.Min(c.Height, o.Height)) continue;   // 不足半行 → 不算同行
```

### Grid 高度必须钉死（`BaseHeight`）

复选框被压窄时 WinForms 会**自动折行把 Height 从 22 涨到 44**，
而 Height 是"谁和谁同行"的依据 → 隐形变化把整行布局带偏。
处理：
- 常规情况：`ApplyRowWraps()` 里把 Height 钉回 `BaseHeight`；
- 例外（独占整行仍放不下，如 733px 的"允许拖动全屏…"）：
  `SyncWrappedHeights()` 用 `TextRenderer.MeasureText(..., WordBreak)` 真正按宽度
  量折行高度，再把它下面的行整体下推。
  **`GetPreferredSize()` 在这里没用**——恒等于 BaseHeight，量不出"要折行"。

### 宽度下限要有"上限"

给 Grow 类加"不得窄于文字"的下限时，**下限本身必须被 `right - baseLeft` 夹住**。
第一版没夹，把 1030px 的整行说明撑到 1030px、冲出分组 365px，比原来还糟。

### `ContentHeightExceeds()` 必须按列数分行

原先写成 `sum(所有分组 Height)` —— 单列对，两列时把 3 行当 6 行算，
"预判一定出滚动条"永远成立，`avail` 多扣 17px，右列刚好被切一条。

### 迭代到不动点（`MeasureAndWrap`）

断行判定↔分组宽度↔滚动条↔内容高度是一个环。破解办法：反复跑
【排布 → 判定 → 撑高】直到"断行集合"不再变化（上限 4 轮，实际 2 轮收敛）。
中途**绝不落地中间状态**——早先为"先定列数"调了一次 `Relayout(probe)`，
probe 比真实 avail 大 17px，各分组宽度停在那上面，
`ApplyOne` 读到的 `ClientSize` 是假的，Shift 类全被压成 20px。
