### ★★ 字号被放大两次：文字被裁掉一半

```
Point 单位的字号，系统已经按当前 DPI 换算过像素高度：
    9pt @ 96dpi  = 12px
    9pt @ 192dpi = 24px   ← 系统自动放的，已经是设计稿的 2 倍
代码里又乘一次缩放系数 s：
    18pt @ 192dpi = 48px
而控件高度只放大 2 倍（20 → 40px）
    → 字高 48px 装进 40px 的框 → 被裁掉一半
```

实测数据：`字高79 > 框高44`。两处错误：`ScaleDesign` 里的控件字体、
`ScaleFlatButton` 里的按钮字体，都删掉乘`s` 的那行。

**分工（改成 AutoScaleMode.None 之后）**：
| 东西 | 谁负责 |
|---|---|
| 控件 bounds | 我们手动乘 `s`（系统不管） |
| 字号 point | 系统按 DPI 自动换算（**什么都不用做**）|

**通则：只有"代码写死的坐标"需要手动缩放，字号绝对不要碰。**

### ★★ 拖动失效的排查：静默的失败路径让排查失去方向

用户报"长按 enter 后左键移动、右键改长宽没反应"，但日志里只有
`触发键激活` / `触发键释放`，中间一片空白。查日志查不出原因，
最后定位到**失败路径一条日志都没有**：

```csharp
if (action == Actions.Nothing) return false;          // 静默
IntPtr hwnd = WindowActions.FindTarget(pt, ...);
if (hwnd == IntPtr.Zero) return false;                // 静默
```

`FindTarget` 有一长串拒绝条件（黑名单/类名/全屏/自身进程/尺寸为0），
命中任何一条用户体验都是"按下去没反应"，日志一个字不留。

**通则：用户报"按了没反应"时，第一件事是确认失败路径有没有留日志。**

修法：新增 `WindowActions.DescribeReject()`，按与 `FindTarget`
**严格相同的顺序**复现每一条判定，报出卡在哪一条；在两个 `return false`
前各记一行 `Log.Trace`（只在 `--trace` 时输出，不影响热路径）。

### 诚实记录：Z序穿透不是根因

我一度判断"浮层 `WS_EX_TOPMOST` 挡住 `WindowFromPoint` 导致拖动失效"，
但 T39 的诊断数据打出来是`WindowFromPoint=3A13EC 目标=3A13EC`
—— **命中的就是目标窗口本身，浮层没抢走命中**。判断错了。

`FindTarget` 的 Z 序穿透（`GetWindow(h, GW_HWNDPREV)`，上限 32 层）
作为防御性加固保留了：前提一旦成立（不同 DPI / 不同 Z 序 / 浮层画得更大），
老逻辑就会直接放弃拖动。但它不是用户那次失效的根因。

### 内存底断言不稳定（不是泄漏）

`--stress` 同一份代码两次跑分别报 +1MB 和 +61MB ——
"取 3 轮最低值"偶尔会连着 3 轮都落在"GC 还没把页还给系统"的窗口里。

### ★★ 不跟手：平移漏了 SWP_ASYNCWINDOWPOS

```csharp
// 改之前
public const uint MOVETHICKBORDERS = SWP_NOZORDER|SWP_NOOWNERZORDER|SWP_NOACTIVATE|SWP_NOSIZE;
public const uint MOVEASYNC       = MOVETHICKBORDERS | SWP_ASYNCWINDOWPOS;
```

`MOVETHICKBORDERS` 漏了 `SWP_ASYNCWINDOWPOS`。缺它时 `SetWindowPos`
会**同步等**目标窗口处理完 WM_WINDOWPOSCHANGING/CHANGED 才返回 ——
目标越复杂、越是跨进程，等待越久，拖动工作线程每帧都被堵住 → 追不上鼠标。

症状特征：**平移比缩放更明显**（缩放走 RESIZEFLAGS，本来就带 ASYNC）。
而 `WindowActions.SetDragRect` 上方注释第 4 点明明写着平移要用 ASYNC
—— **注释和实现自相矛盾**，注释对、代码漏了。

**通则：常量定义里"看起来等价"的两套标志位，要逐个比对每一个 bit，
不能只看名字相似就当成一样。**

### ★★ 下拉框显示为空但点开有选项

`DropDownStyle = DropDownList` 时，框里显示什么**完全由 SelectedIndex 决定**。
一旦停在 -1，框就是空白；而下拉列表各项都还在 ——
**Items 集合和"当前选中态"是两回事**。`Items.Clear()` 会把 SelectedIndex 重置成 -1。

加固：`SelectId`/`SelectAction` 保证"永远至少选中一项"，
设完索引后补 `if (c.Items.Count > 0 && c.SelectedIndex < 0) c.SelectedIndex = 0;`

T41 必须用**非默认**配置测（Dashed/Mint/Custom/None）——
默认值恰好等于第一项，"碰巧就对了"测不出匹配逻辑。

### ★★ 底栏按钮文字与框没适配（两个独立原因）

**1. 用错度量 API**：`g.MeasureString`（GDI+）算宽度，却用 `TextRenderer`
（GDI）落笔，还手工减 1 推位置。两套 API 基准不同，高 DPI 下偏差被放大。
正解：把整块矩形交给 `TextRenderer` + `HorizontalCenter|VerticalCenter`，
让它的对齐标志负责居中。

**2. 高度不在一个尺度**：断言量出 `按钮高 52 输入框高 39 差 13`
（ComboBox 有内部留白，实际渲染高度 ≠ 设定值）。按钮 32→20（→40），pager 58→46。

另外按钮圆角写死 6 没跟 DPI 缩放，改成 `6 * CurrentUiScale`。

**通则：自绘控件里，凡是用 A 算、用 B 画，就是隐患。**

### ★ 核心根因：AutoScaleMode.Dpi 与布局基准坐标系错位

本窗口控件坐标全是代码写死的 96 DPI 设计稿值（`Label("触发键", 16, 31, 60)`），
原设了 `AutoScaleMode = AutoScaleMode.Dpi` + `AutoScaleDimensions(96,96)`。
WinForms 在首次 Show 时 `PerformAutoScale()` 会缩放子控件 bounds，
而 `MarkBase()` 在构造函数里采样（缩放之前）→ 基准 110 vs 实际 220，
`c.Top = BaseTop + dy` 把每行都"缩"回去，行距 26 → 13，行行相叠。

**踩过的弯路（别再走）**：先试"事后重新采样基准"(`RebaseAfterAutoScale`)，
靠相邻行距比值反推缩放系数 —— 实测系数是 **1.0，等于白改**。
因为这台机器上**字体被放大了但控件 bounds 没有等比放大**（位置是代码显式赋的），
是"字变大、行距没变"的半吊子状态，行距比当然量不出系数。

**正解**：`AutoScaleMode = AutoScaleMode.None` + 自建 `ScaleDesign(groups)`，
在 `MarkBase()` **之前**把设计稿值按 `DeviceDpi/96` 缩放一遍。
配套把布局常量改成 `S()` 缩放的实例属性（GroupWidth / SingleColumnClientWidth /
GroupInnerPadLeft / ScrollEdgeMargin），窗体尺寸、MinimumSize、按钮、两列阈值全走 S()。

**约定**：MarkBase 之后任何地方不许改基准坐标；"基准+增量"的增量必须是这一轮的总量。

### ★ Anchor 双重拉伸：功能失效的真正根因

现象：`"开机自启"`下拉框设计稿宽 430，实际 `BaseW=1502`；下拉框内容被切光、
"以管理员重启"按钮 `L=1452` 被顶到 1072 宽的分组外面。

时序（关键）：
```
设计稿 430 → 【WinForms 锚定拉伸】→ 751 → 【ScaleDesign ×2】→ 1502
```
控件带 `Anchor = Top|Left|Right` 时，`ResponsiveGroupPanel` 构造就把分组塞进
`TableLayoutPanel` 并定好列宽 —— 系统锚定逻辑在 `ScaleDesign()` **之前**
已经把控件拉宽过一次了。

后果链：`baseRightGap = 1072 - (180 + 1502) = -610`（负数）→ `ApplyOne` 的 Grow 分支
把右边界算到 `innerRight + 610` → 下拉框反超分组 602px；
`LeftBarrier()` 还把这个撑宽宽度当成"左边的墙"，把按钮推到 L=1452。

修法：`ScaleDesign()` 开头把所有分组及其子控件的 Anchor 全摘成 `Top|Left`，
再做缩放。（敢这么做是因为 `MarkBase()` 里本来就把 Anchor 改成 `Top|Left`。）

**通则：任何"自己接管布局"的代码，都必须先把系统的自动机制摘干净。
系统锚定和自绘缩放同时作用，就是双重计算。**

## 12:36 ★ 关键教训：改了代码但没部署，用户等于什么都没看到

用户原话："你做了太久了……真正的改善我到现在都没看到，我非常怀疑你真实的能力。"

**根因（必须先说清）**：整轮修复只落在 `bin/` 和 `_rel/`，**桌面 `HoldDrag.exe` 一直是 11:39 的旧版**。
用户每次双击的都是旧程序，当然看不到任何变化。**"改完 → 发布 → 部署 → 冒烟"是一条不可省的链**，
任何一环漏掉，前面的工作全部归零。以后每轮收尾必须做完整条链并核对 MD5。

### 本轮定位并修掉的真实缺陷

1. **设置窗口尺寸上限写死 2400**（`Config.Normalize()`）
   - 用户屏幕 3840 宽，窗口拉宽后 `Normalize()` 把它压回 2400
   - 表现："我明明拉得更宽了，下次打开又变回去"

## 13:20 ★★★ 根因终于找到：进程是 DPI 不感知的（"基本功能全没了"）

用户原话："基本的功能都没有了呀……按 enter 键之后触发阈值，我们通过左键和右键来触发相应的功能，现在这个功能没有了。"

### 定位过程（靠日志，不靠猜）

我上一轮加的诊断日志直接给出了答案：
```
[诊断] FindTarget 没找到目标…… 原因=WindowFromPoint 返回空（桌面/无窗口区域） 坐标=2182,1440
```

**关键推理**：2182 > 1920 —— 而该进程的逻辑屏幕宽度只有 1920。
说明钩子给的是【物理坐标】(3840x2160 屏)，进程却在【逻辑坐标】(1920x1080) 里工作。

于是系统把 2182,1440 再放大 2 倍 → 4364,2880 → **跑到屏幕外** → WindowFromPoint 返回空
→ FindTarget 返回 0 → 左键右键全部失效。

### 决定性实验：同一个 exe，不同路径运行，DPI 感知级别不同

md5 完全相同的文件：
| 运行位置 | DPI 感知 |
|---|---|
| `/tmp/hdtest/a.exe` | 每显示器感知(2) ✓ |
| 项目目录 `./_rel/HoldDrag.exe` | 每显示器感知(2) ✓ |
| **`C:/Users/64381/Desktop/HoldDrag.exe`** | **不感知(0) ✗** |

→ 用户双击的正是桌面那个。**这就是"改了多少轮都看不到改善"的另一个原因。**

### 三层防护（都实现了）

1. **app.manifest 声明 PerMonitorV2**（进程启动时最先生效）
2. **Main 第一条语句调 SetProcessDpiAwarenessContext(PerMonitorV2)**
   —— 实测在某些环境返回 False（被锁死），所以还需要第 3 层
3. **`CoordSpace.cs` 坐标换算**（真正兜住的那层）
   - 用 `GetAwarenessFromDpiAwarenessContext` 判感知级别
   - 不感知时用 `GetDeviceCaps(DESKTOPHORZRES)` 取【物理】分辨率
     （★ 必须用 DESKTOPHORZRES，HORZRES 返回的是被虚拟化过的值，算出来恒等于 1，白算）
   - 算 `scale = 逻辑宽 / 物理宽`（本机 = 0.5），把钩子的物理坐标乘回去

### ★ 换算点必须放在"真正的边界"上

第一版把换算放在 `Coordinator.OnMouse` —— **错的**。
`OnMouse` 也会被自检/内部逻辑直接调用，那些调用传进来的已经是逻辑坐标，
再乘一次比例 → 实测"拖动只走了一半、窗口追不上光标"（11 条用例报红）。

正解：放在 **`HookEngine.MouseCallback`**（系统物理坐标进入本进程的唯一入口），
且必须在 `MarkSeen` 之前 —— 看门狗拿这里记的位置和 `GetCursorPos()`
（对不感知进程返回逻辑坐标）比对，两者必须同空间，否则会误判"钩子已死"。

### 另一个真实 bug：ScaleDesign 在 100% DPI 直接 return

```csharp
private void ScaleDesign(...) {
    float s = UiScale;
    if (Math.Abs(s - 1f) <= 0.001f) return;   // ← 100% 直接返回
    ...
    if (_btnDefaultsRef != null) ScaleFlatButton(_btnDefaultsRef, s);  // ← 被挡在外面
```
底栏按钮的自适应高度因此**永远不执行**，100% 下按钮 20px 装不下 17px 的字
→ 用户报的"按钮字跟按钮没适配"。修：把 FlatButton 处理提到提前返回之前。

### 固定高度无解，必须按字体自适应

- 设计高 20 → 200% 下 40px 配 39px 输入框 ✓，但 100% 下 20px 装不下字 ✗
- 设计高 26 → 100% 下 26px ✓，但 200% 下 52px vs 输入框 39px 差 13 ✗

根因：TextBox/ComboBox 高度是【按字体自动算】的，FlatButton 是自绘控件、高度写死 ——
一个跟随字体一个写死，任何固定值只能对上某一个缩放档。
正解：`ScaleFlatButton` 里兜一个下限 `TextRenderer.MeasureText(...).Height + 8`。
