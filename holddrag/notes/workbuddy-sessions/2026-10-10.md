### 技术要点（下次做同类工具可直接复用）
- **刻意不用系统原生拖动循环**（`WM_NCLBUTTONDOWN` + `HTCAPTION`）。原生循环一旦启动就由系统接管，
  拦不到"双击左键/双击右键"这两个用户明确要求的功能。因此只能自己 `SetWindowPos` + 自己实现边缘吸附
  （AltSnap 也是这条路）。代价：Win11 的 Snap Layouts 面板不会弹出。
- **长按状态机**：按下瞬间就吞掉 → 阈值内松手用 `SendInput` 补发一次完整按下+抬起（Enter 正常功能不受影响）
  → 超过阈值进入激活态 → 松手退出。**代价：按住 Enter 连续换行会被压成单次**（要区分长按和连发，原理上无法两全）。
- **钩子三条纪律**：① 回调里绝不阻塞式 `SendMessage`（超过 `LowLevelHooksTimeout` 会被系统静默摘钩）；
  ② 带 `INJECTED` 标志的事件必须原样放过，否则自己触发自己死循环；③ 回调抛异常必须就地吞掉，
  绝不能抛回非托管调用方。委托必须存字段否则被 GC 回收 → 非托管野指针崩溃。
- **浮层窗口**（吸附高亮 / 尺寸提示）必须同时带 `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TRANSPARENT`，
  且句柄在启动时提前创建，避免第一次拖动时因建窗而卡住输入回调。
- **`Application.ExecutablePath` 的坑**：以 `dotnet HoldDrag.dll` 方式启动时它返回 dotnet.exe 的路径，
  会让内嵌图标取错、开机自启注册错。已用 `Environment.ProcessPath` 兜底（`AppPaths.cs`）。

## 修复：exe 启动报 14001「并行配置不正确」

**用户报告**：`应用程序不能启动，因为应用程序的并行配置不正确`（Windows 错误 14001
`ERROR_SXS_CANT_GEN_ACTCTX`）。即 SxS 加载器拒绝 exe 里嵌的清单，进程在托管代码之前就被杀，
日志里什么都看不到。

### 根因（已用实验证实，不是推测）
**`app.manifest` 的 XML 注释里写了双连字符 `--`**：

```xml
<!-- 这样 --selftest / --no-elevate 两个诊断参数才能... -->
```

XML 规范禁止注释内出现 `--`。整份清单因此非法 → SxS 解析失败 → 14001。
Windows 自己的解析器判词：`XML 注释中不能包含"--"，并且"-"不能是最后一个字符。第 7 行，位置 8`。

### 我是怎么定下这个结论的（关键：先证伪了自己）
1. 第一直觉是「中文注释是非 ASCII，无 BOM 会被按 ANSI 码页误解码」——**这个猜测是错的**。
   做了单一变量实验：把旧清单里每个非 ASCII 码位换成 `x`、其余字节一字不动 → **依旧 14001**。
2. 于是改用 `CreateActCtxW` 探针（`_diag/ManifestProbe/`，独立 csproj，放在项目目录之外
   以免被主项目源码通配捞进去）直接问 SxS 接受不接受。它**精确复现了 14001**。
3. 再逐一隔离：旧清单**只把 `--` 改成 `- -`**（中文、`assemblyIdentity`、DPI 段、`longPathAware` 全保留）
   → **立刻被接受**。到此根因闭环。
4. 顺手证伪了其余嫌疑：`<assemblyIdentity>`（有无 `type="win32"`）、`<dpiAware>`/`<dpiAwareness>`、
   `<longPathAware>`、`windowsSettings` 混三套命名空间——**全部合法，全部通过**。

**可复用教训**：manifest 是「进程起来之前」的解析，报错完全不提清单内容，只能靠探针定位。
`CreateActCtxW` 配合 `ACTCTX` 结构体的 file 模式是本机可用的判定手段（module 模式需要
`LOAD_LIBRARY_AS_DATAFILE` 的 HMODULE，实测返回 126，走不通，别再用）。
另外：**构建里加 XML 合法性预检**（`build.bat` 已内置 PowerShell `[xml]` 校验，非法即中止构建）。

### 顺带做的两处改动
- **清单收窄成最小形态**：只留 `trustInfo`（`asInvoker`）+ `compatibility`（Win10/Win8.1），
  无注释、纯 ASCII（652 B）。既去掉注释隐患，也把非常规内容降到最少。

  冒烟日志实测 `SetHighDpiMode(PerMonitorV2) => True`，证明 PerMonitorV2 确实生效、没有丢行为。

### 验证结果
- 新旧两次构建的**单文件 bundle 结构完全一致**（含尾部那些字节），说明 .NET 10 的 bundle 布局
  就是那样，此前「文件被截断」的怀疑是**误判**（`rfind` 命中的是 apphost 内置的常量表，不是文件尾标记）。
- bundle 载荷逐字节校验：`HoldDrag.dll` / `runtimeconfig.json` / `deps.json` 三个内嵌条目与多文件产物**完全一致**。

于是先下载真实源码再动手（**不要靠推理改手感问题**）：
`curl -sL -o altsnap.tar.gz "https://codeload.github.com/RamonUnch/AltSnap/tar.gz/refs/heads/main"`
（`git clone --depth 1` 会挂；`file` 命令在本 shell 不可用）。解压到 `_diag/altsnap-src/AltSnap-main/`。
拖动内核全在 `hooks.c`：`WorkerThread` / `MouseMoveNow` / `MoveWindowNow` / `LowLevelMouseProc`。

### 根因一（就是"哆嗦"本身）：低级鼠标钩子里吞掉了 WM_MOUSEMOVE

- 旧代码在拖动期间对 `WM_MOUSEMOVE` 返回 `true`（吞掉）。而在 **`WH_MOUSE_LL` 钩子里吞掉鼠标移动，
  系统会认为这次移动被拒绝，光标就停在原地不动**。光标不动 → 钩子拿到的坐标不再变化 → 窗口只能原地抖。
- 三条独立证据：①微软 `LowLevelMouseProc` 文档；②UnKnoWetCheats 的"用 LL 钩子冻结鼠标"帖
  （明说 blocking WM_MOUSEMOVE "CANNOT move your mouse, only stop"）；③DaniWeb 改鼠标灵敏度的例子——
  它必须自己 `SendInput` 补一次移动，正因为拦下原始移动后指针就不动了。
- AltSnap 的 `LowLevelMouseProc` 在移动分支上**始终 `CallNextHookEx`**，从不吞移动消息。
- **修法**：`Coordinator.OnMouse` 的移动分支改成「永不吞」，并删掉我自己造的配置项
  `SwallowDragMouseMoves`（它把"要不要吞消息"和"要不要用消息驱动拖动"捆在一起，怎么调都是错的）。

### 根因二（"时灵时不灵"）：用 GetAsyncKeyState 校验触发键是否按住

- `TriggerState` 有个 2000ms 看门狗，用 `GetAsyncKeyState` 判断触发键还按着没有。
  但长按方案**必须吞掉触发键的按下事件**，而**事件一旦被吞，系统层面就完全看不到这个键被按过**。
- **实测证据**（`_diag/KeyStateProbe`，独立探针）：钩子里吞掉 F13 的按下 → `GetAsyncKeyState=0x0000`；
  同一时刻放行的 F14 → `0x8001`。钩子计数确认被调用过 1 次，排除"钩子没装上"。
  即任何基于 `GetAsyncKeyState` 的看门狗，在"按键正被按住"时都必然判为"已松开"，
  于是每 2 秒误判一次、把激活态打掉，要等自动重复重新计时 600ms 才恢复。
- **修法**：删掉看门狗。状态机改纯事件驱动，并且**本身能自愈**——
  真丢了抬起时 `_held` 仍为 true，用户再点一下触发键也只会被吞（不会重复激活），
  紧接着那次正常抬起就会 `EndHold()` 清干净。回归用例 `T23`：按住 2.5 秒激活态必须一直在。

### 顺带按 AltSnap 复刻的三处（这部分是硬要求，不是我加的）

1. **钩子回调搬去工作线程**（`DragWorker.cs`，对应 AltSnap `WorkerThread`）。
   微软文档明写：回调超 `LowLevelHooksTimeout` 钩子会被**静默摘除**且**无法察觉**，
   必须"交给 worker 线程后立刻返回"。旧代码在钩子里 `EnumWindows` + 逐窗口 `GetClassName` + `SetWindowPos`，
   是最典型的会超时写法。工作线程还会**合并连续堆积的移动，只执行最新一个**（AltSnap 有意为之）。
2. **位置用「光标绝对坐标 − 固定偏移」推导**（AltSnap `posx = pt.x - state.offset.x`），
   **不做增量累加** → 丢事件/合并事件都不会累积漂移。
3. **写窗口的三档标志**（`WindowActions.SetDragRect`，对应 `MoveWindowNow`）：
   尺寸变了 → `RESIZEFLAGS`；只平移且可缩放 → `MOVETHICKBORDERS`；只平移且不可缩放 → `MOVEASYNC`。
   走异步后**必须补一次 `WM_SYNCPAINT`**（否则窗口"堵在 WM_MOVE 队列里滑过去"，看着一卡一卡）。
   另外进入/退出拖动发 `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE`（`NotifySizeMove`，对应 `NotifySizeMoveStaEnd`），
   终端类程序靠它切字符网格对齐。
4. `Begin` 的起点坐标改成**用钩子里那次按下事件的 pt**，不再另外调 `GetCursorPos()`
   （AltSnap `init_movement_and_actions(pt)` 同此）。原来两个来源不同，基准和更新可能对不上。

### v2 大改（2026-10-10 深夜）—— 设置空白 / 残影 / 越拖越卡 / 通用性 / 权限开关 / 托盘暂停

**A. 设置窗口空白（头号 bug）**：`SettingsForm.BuildUi()` 建了 g1..g4 却**从未 `Controls.Add`**，
所以窗体上一个控件都没有。已改为 6 个分组并显式 Add。永久回归：
`SettingsForm.VerifyLayout(Form)` + 自检 `T22`（断言分组数>=6 且每个分组非空）。
→ **教训：WinForms 里"创建了控件"和"挂到父容器"是两件事，写动态布局必须有一条断言兜底。**

**B. 残影 + 越拖越卡**：三个独立成因，逐个修掉。
1. WinForms `Form` + `Opacity` + `SetBounds` + `Refresh` —— **移动立刻生效、旧位置要等下次 WM_PAINT 才擦**，
   中间态被看见；叠几百次就是一串影子。
2. 没节流，每秒几百次 `SetWindowPos` 灌爆目标窗口消息队列 → 积压 → 越拖越卡、擦得越慢、残影越明显。
3. `Opacity` 走 layered 慢路径，每帧重合成。
→ 改法：外框用 **`SetWindowRgn` 圆环**（不透明、无中间态，物理上不可能残影）；
预览用 **`UpdateLayeredWindow`**（位置+像素原子提交）；`SetWindowPos` 后按刷新率节流；
重活（ForceForeground / EnumWindows）全部 `Post` 到工作线程。
→ 用户已明确：**删掉拖动半透明、删掉尺寸提示**，改为"被接管的窗口外面套一圈强调色圆角外框"。

**C. `WM_PAINT` 不 `ValidateRect` = 无限重画**（自查时卡死很久的根因）：
处理了 `WM_PAINT` 却没有 `BeginPaint/EndPaint` 也没有 `ValidateRect` → 无效区永远无效 →
系统无限重发 `WM_PAINT` → `Application.DoEvents()` 永不返回。**必须在 finally 里 ValidateRect。**

**D. 通用性 —— 钩子被 Windows 静默摘除**（这才是"有些软件用不了"的真因）：
回调超过 `LowLevelHooksTimeout` 就被摘，**且没有任何 API 能得知**。表现随机、系统越忙越容易触发。
→ 加 `HookWatchdog`（抄 AltSnap `REHOOK_TIMER`）：每秒比对 `GetCursorPos` 与钩子最后见到的位置，
光标动了钩子没动 = 死了 → `Reinstall()`。自检 T28 真的卸掉钩子再动鼠标验证。
→ 顺带：全屏/无边框窗口默认跳过（可开）、用户黑名单、被完全遮住的窗口不参与对齐（利用 EnumWindows 的 z 序）。

**E. 高频屏节流陷阱**：Windows 默认定时器精度 15.6ms，不调 `timeBeginPeriod(1)` 的话
