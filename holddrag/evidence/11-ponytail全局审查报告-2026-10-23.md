## What this repo does:

一款 Windows 桌面长按拖窗工具（AltDrag 思路的 C# 重写，.NET 10 / WinForms / x64）。以管理员权限单实例运行：低层键盘鼠标钩子（`HookEngine` + `HookWatchdog`）捕获输入，`Coordinator` 状态机判定"触发键按住 + 移动 → 拖动窗口"，`DragEngine`/`DragWorker` 在专用线程上按显示器刷新率节流地 `SetWindowPos`，`OverlayWindow`（独立线程 + 原始 Win32 分层窗口）绘制激活框/大小提示/投影。配置三级备份轮换 + tmp 原子写；更新走 GitHub Releases + TLS + 哈希校验 + `.old` 接续清理；设置页为自绘卡片式 UI（深浅色双 Tokens、WM_NCCALCSIZE 无标题栏、DPI/主题变化整体重建）。自带 `--selftest`（约 800 项断言）、`--visualcheck`、`--framebench`/`--frameprobe` 压测探针。

负载画像：单用户桌面应用、单实例、必须管理员；没有多租户、没有服务端、没有并发写入冲突面。审查按此画像定级：**用户可感知的功能失效 > 静默数据丢失 > 死代码/维护性 > 整洁**。

## Must fix

### 1. 录制界面按下纯修饰键 → 绑定死触发键 `K:0x00`

- **What this is**：`SettingsForm.ProcessCmdKey`（20617-20639）录制触发键；`KeysUtil.ResolveRecordedKey` default 分支（5698-5706）。
- **Problem**：录制时只要按下 Ctrl / Shift / Alt 或任何"纯修饰键组合"（不含其他键），`keyData & Keys.KeyCode` 等于 `Keys.None`(0)，default 分支算出 `"K:0x00"` 并直接绑定。`ToVirtualKey("K:0x00")` 得到 vk=0，而钩子事件里永远不会出现 vkCode=0 的真实按键——触发键从此永久失效。界面提示却是"已绑定：虚拟键 0x00"（`DisplayName` 5810），用户看不出任何异常，只会觉得"长按拖动突然失灵"；该值还会写入配置，重启后依然失效。这是本工具最常用的一个设置操作（录音时习惯性按着 Ctrl），命中概率很高。
- **Fix**：`ProcessCmdKey` 里先判 `keys == Keys.None` → 提示"修饰键不能单独作为触发键，请再按一个主键"，`return true` 保持录制、不绑定；`ResolveRecordedKey` 对 0 返回 null（与鼠标按钮的 null 语义一致）。
- **If we skip it**：一个再自然不过的操作就静默废掉核心功能，且跨重启复现、用户无法自愈（不会有人去看日志）。

### 2. `ConfigStore.Save` 吞掉所有异常，设置页却显示"已保存并立即生效"

- **What this is**：`ConfigStore.Save`（1215-1238）；调用方 `SettingsForm.Save`（20708-20736）与 `ConfigStore.Apply`（1240-1246）。
- **Problem**：catch 里只有 `Log.Error`，不抛、不返回。磁盘满 / 目录被锁 / 文件被占用时，设置页照常显示绿色"已保存并立即生效"，用户以为生效了；重启后设置全部回退。典型的静默数据丢失 + 误导性成功反馈。
- **Fix**：`Save` 返回 bool（失败原因一并带出），`Apply` 透传；设置页失败时状态栏变红显示"保存失败：原因"，并明确告知"本次修改未持久化"。
- **If we skip it**：概率低但每次发生都是"设置丢了还不知道为什么"，且与 #1 叠加会让用户彻底失去信任。

### 3. `RelaunchElevated` 拼命令行不加引号

- **What this is**：`Program.RelaunchElevated`（8944-8970），对照 `Updater.ApplyAndRestart`（385-389）。
- **Problem**：`Arguments = string.Join(" ", list)` 不带引号；而同文件的 ApplyAndRestart 对 `--updated-from` 路径是加了引号的——同一规则两处不一致。安装路径含空格（`C:\Program Files\...`、用户目录带空格）时 `--updated-from "…\HoldDrag.exe.old"` 被截成多个参数，新版接续实例拿不到旧版路径，`.old` 备份清不掉（`CleanupOldVersion` 对空参安全所以不崩，但垃圾文件永久残留）。
- **Fix**：抽一个小 helper 统一给每个参数包引号，两处共用；`--updated-from` 场景至少按 ApplyAndRestart 的写法补齐。
- **If we skip it**：带空格安装路径 + 更新链路下旧版备份残留；参数截断属于"总有一天踩到"的雷。

### 4. v1.6.0 已发版，但 git 工作区未提交、未打 tag

- **What this is**：`git status` 显示 README / dist exe+pdb / PRD / HoldDrag.cs / AssemblyInfo 全部 modified（+1514/-798），最新 tag 仍是 v1.5.0；GitHub Release 已挂 v1.6.0 产物。
- **Problem**：发版文物与源码历史断档——日后无法回到"发版时刻的源码"复现或比对，evidence 自检记录指向一个不存在的 commit。
- **Fix**：提交 v1.6.0 工作区（含 evidence 自检记录；`st.txt` 确认是草稿就删掉），打 `v1.6.0` tag 并推送。
- **If we skip it**：每次后续发版的 diff 基线都是错的，回归定位成本持续放大。

## Should fix

### 5. `Save()` 失败时同一个 message 连弹两个 MessageBox

- **What this is**：`SettingsForm.Save`（20726 + 20728-20731）。
- **Problem**：开机自启失败时先弹 Exclamation 再弹 Asterisk，内容完全相同。
- **Fix**：删掉 20728-20731 的重复弹窗，保留带操作指引的那一个。
- **If we skip it**：纯体验磨损，但"连点两个一样的框"很损专业感。

### 6. `MovePreviewMode` 被 `Normalize` 钉死 `"FullWin"`，Outline 分支成片死代码

- **What this is**：`AppConfig.Normalize`（974）；`DragEngine` 3003/3209/3288 与 `ShowOutline`（3696-3716）。
- **Problem**：全树没有任何 UI 写入 `MovePreviewMode`（仅自测 10838 会设 Outline 验证该路径），Normalize 无条件覆写为 FullWin → Outline 渲染路径生产环境不可达，但分支、位图分配、绘制代码全在。读代码的人会被误导，未来改拖动渲染时可能在永远不跑的路径上浪费时间。
- **Fix**：二选一——删掉 Outline 相关分支与配置字段；或在设置页开放该选项并去掉 974 的钉死。
- **If we skip it**：一片"看起来活着"的死代码长期滞留。

### 7. `MoveRate/ResizeRate` 死条件块

- **What this is**：`Normalize`（987-993）。
- **Problem**：`if (MoveRate == 2 && ResizeRate == 4) { 置 1 }` 紧跟无条件 `MoveRate = 1; ResizeRate = 1;`——条件块永无效果，纯历史残留。
- **Fix**：删 987-991；若本意是旧配置迁移，应放 Load 后一次性处理，不该放每次都会跑的 Normalize。
- **If we skip it**：读代码的人会以为 2/4 是合法值并去找对应逻辑。

### 8. `PostPairedButtonUp` 零调用死代码

- **What this is**：1730-1772，外加 `PairedUpProbe`、`PhantomUpSentForTest`、`LastPairedUpForTest` 观测字段（共约 50 行）。
- **Problem**：注释自己已说明它是"触发键激活后左键仍点穿到下层窗口"这个已修 bug 的根因，生产路径不再调用。留着有被误接线的风险——注释本身就是警告。
- **Fix**：删除；自检中"PhantomUpSentForTest 恒 0"的断言改为常量断言或一并移除。
- **If we skip it**：危险诱惑：谁想把"配对抬起"接回去，就把点穿 bug 请回来。

### 9. `_inset` 同一函数算两遍，第二次在锁外

- **What this is**：`DragEngine` 开始拖动会话处（2978/2995 vs 3002）。
- **Problem**：锁内已写入 `_inset`，锁外又 `ComputeInset` 一遍再赋值。两次结果相同所以现在无实际故障，但 worker 线程在 2995→3002 之间读到哪份值取决于时序——典型的数据竞争写法，且多一次 P/Invoke。
- **Fix**：删掉 3002（保留锁内赋值），或删掉锁内赋值只留锁外一次；二选一，别留两份。
- **If we skip it**：一旦有人改 `ComputeInset` 的耗时或结果，竞争立刻变成真 bug。

### 10. Shadow 缓存键 XOR 位域重叠

- **What this is**：`DrawShadow`（4749）。
- **Problem**：缓存键把 w/h/半径/颜色/pad 用移位 XOR 拼 long，但 `color.ToArgb()` 占 bit 0-31，与 h 的 bit 22-35、r 的 bit 9+ 重叠 → 不同（颜色, 尺寸）组合可能算出同一个 key，命中用旧半径/旧颜色构建的缓存位图。视觉影响很小（同一浮层内颜色/半径通常不变），但键设计本身是错的。
- **Fix**：改用元组/字符串键，或把色值移到不重叠高位；XOR 改加法/拼接更防撞。
- **If we skip it**：小概率、难复现的视觉错影。

### 11. `DragWorker.Post` 投递失败时 TryDequeue 可能删错任务

- **What this is**：`DragWorker.Post`（3808-3818）。
- **Problem**：任务从队尾入队，`PostThreadMessageW` 失败后 `_work.TryDequeue()` 从队首取——ConcurrentQueue 是 FIFO，移除的是最早的任务而不是刚入队的那个，语义反了。
- **Fix**：失败时记日志即可（线程消息队列满极罕见），别做不对应的出队。
- **If we skip it**：队列满时静默丢失最旧的渲染任务，且丢失的是"错的"那个。

## Nice to have

### 12. `_idleReleaseTimer` 从不 Dispose

- **What this is**：3474/3490（懒创建），3519-3520（Stop/Start）。
- **Problem**：DragEngine Dispose 时没有释放它。
- **Fix**：Dispose 里补 `_idleReleaseTimer?.Dispose()`。
- **If we skip it**：进程退出时由 OS 回收，纯整洁问题。

### 13. `Updater.Download` 先删后移的窗口期

- **What this is**：655-659。
- **Problem**：`File.Delete(targetPath)` 后 `File.Move(text, targetPath)`，中间窗口期目标文件不存在；`File.Move(text, targetPath, overwrite: true)` 一步到位。finally 删 `.part` 在成功后虽无害（文件已移走）但顺序可读性差。
- **Fix**：用带 overwrite 的 Move；finally 保持即可。
- **If we skip it**：极小窗口期的替换脆弱性。

### 14. 回滚也失败时"至少有一个能跑的 exe"表述过强

- **What this is**：`ApplyAndRestart` 377-382 与 README/提示文案。
- **Problem**：回滚分支只记日志——旧 exe 已删、新 exe 没移成功时，可能两者皆无。
- **Fix**：文案软化为"可能需要在官网重新下载"；或加最后兜底（把 `.part` 复制回目标路径）。
- **If we skip it**：极端故障路径下用户被文案误导。

### 15. 未跟踪的 `st.txt`

- **What this is**：仓库根未跟踪文件。
- **Fix**：确认是草稿就删除，或收入 .gitignore。
- **If we skip it**：仓库里永远躺一个来源不明的文件。

## Verdict:

架构是健康的，核心风险不在框架而在边界。跨线程模型（浮层独立线程、钩子看门狗、日志异步队列、配置备份轮换、TLS + 哈希校验的更新链）都经得起看；`--selftest`/`--visualcheck`/探针设施是真资产而非摆设。真正会伤到用户的是四个 Must fix：**#1 让最常用的设置操作能静默废掉触发键，#2 让保存失败伪装成成功，#3 在带空格路径上截断更新参数，#4 让已发版产物与源码历史脱钩**。建议按 1 → 2 → 4 → 3 的顺序处理（#4 是纯 git 操作，随时可先做）；Should fix 的 #5/#7/#8 是几分钟的删除作业，#6 需要先定产品决策（删功能还是开放选项）。

## Lean:

全树没有任何 `shortcut:` / `ponytail:` 债务标记，与"没有敷衍实现"的印象一致。审查中没有发现为省事而牺牲正确性的写法；发现的问题集中在"边界条件没想到"（修饰键录制、保存失败、引号）和"历史残留没清"（死代码、死条件、重复计算）。保留 `PostPairedButtonUp` 的注释式警告是好事——它防止了下一个人重犯点穿 bug。
