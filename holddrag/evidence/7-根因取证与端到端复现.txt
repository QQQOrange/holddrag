========================================================================
第六轮：用户「按 Enter → 很快按下左键 → 立刻移动，窗口完全拖不动」
        —— 端到端复现、根因取证、修复与验证
========================================================================

用户原话（本轮回执）：
  「我具体的操作流程就是我按 enter 然后快速的按下左键，这时候窗口的外框显示被样式
    包围，但确实这时候鼠标怎么动这个窗口都移动不了……
    如果我按住左键过一段时间再移动，这时候是能够顺利移动的，右键也能够顺利发挥功能，
    但就是不知道为什么按下 enter 之后快速的按下左键就是不能实现功能。」

→ 用户给了一个决定性的对照：**「按下左键后等一会儿再移动」正常 /「按下左键就立刻移动」失败**。
  两者唯一的差别 = **触发键到 200ms 阈值之前，鼠标有没有已经在动**。


------------------------------------------------------------------------
一、先把用户的操作时序变成可重复的机器时序（InputE2E 新增模式）
------------------------------------------------------------------------
工具：work/inpute2e/InputE2E.cs（用 SendInput 注入真实输入，dwExtraInfo=0，
      对被测进程而言与真人输入完全等价；★ SetCursorPos 不产生输入事件，低级钩子看不到）。

新增模式（每个模式都以「目标窗口中心」为指针起点，逐帧记录窗口位移）：
  simult   按 Enter → 30ms → 按左键 → 等 700ms（越过阈值）→ 逐帧移动
  sequ     按 Enter → 420ms（已激活）→ 按左键 → 逐帧移动
  tap      按 Enter → 40ms → 按左键、50ms 后抬起 → 再移动     （用户「按一下」）
  taphold  按 Enter → 点一下左键 → 再按住左键 → 移动
  fastmove 按 Enter → 20ms → 按左键 → **不等待，立刻逐帧移动**（左键全程按住）★
  nomove   按 Enter → 按左键 → 完全不动鼠标

------------------------------------------------------------------------
二、复现结果（三种状态对照；期望位移按"跟手"判定）
------------------------------------------------------------------------
  mode=tap       修复前 +0,+0      修复后 +0,+0      （点按后已松手，按住语义下本就不该拖）
  mode=taphold   修复前 +150,+60   修复后 +150,+60   ✔
  mode=simult    修复前 +150,+60   修复后 +150,+60   ✔
  mode=sequ      修复前 +150,+60   修复后 +150,+60   ✔
  mode=fastmove  修复前 +0,+0 ✘   修复后 +200,+80 ✔  ★★★ 用户报障场景

fastmove 修复后的逐帧轨迹（每步期望 +25,+10）：
  move1  cur=875,540   实际 +0,+0     ← 触发键还没到阈值
  move2  cur=900,550   实际 +0,+0
  move3  cur=925,560   实际 +0,+0
  move4  cur=950,570   实际 +0,+0
  move5  cur=975,580   实际 +25,+10   ← 激活，开始接管
  move6  cur=1000,590  实际 +50,+20
  ...
  move12 cur=1150,650  实际 +200,+80
⇒ 从激活那一刻起**每一步都严格 +25,+10**，即 1:1 跟手。
  前 4 步落在 200ms 阈值内 —— 触发键尚未激活，任何实现都不可能动，属设计边界。

三、真凶（现场日志抓现行，%AppData%\HoldDrag\holddrag.log 21:07:47）
------------------------------------------------------------------------
21:07:47.473 [诊断] 鼠标键按下 键=0 触发[按住=True 激活=False] 缓冲=False
                   阈值期按住=False 已放行=False 拖动中=False 坐标=850,530
21:07:47.635 [诊断] 激活瞬间清点缓冲 缓冲[True,False,False]
                   阈值期按住[True,False,False] 已放行[False,False,False]
                   物理按下[False,False,False]  坐标=950,570          ← ★★★ 就是这一栏
21:07:47.635 触发键激活
21:07:48.073 [诊断] 鼠标键抬起 键=0 触发[按住=True 激活=True] … 拖动中=False

读法：
  · 左键**确实按着**：47.473 收到按下、48.073 才收到抬起，中间 600ms 一直按住；
  · 缓冲账里**确实有这条按下**（`缓冲[True,…]`、`阈值期按住[True,…]`）；
  · 可 `GetAsyncKeyState(VK_LBUTTON)` 报 **False**（`物理按下[False,False,False]`）。

老代码在激活瞬间的第二道关卡正是：

    if (!IsButtonPhysicallyDown(i))          // 系统的这句"没按着"
    {
        _bufferedDown[i] = false;            // → 把刚收到、还热乎的缓冲按下整条丢掉
        _heldDuringHold[i] = false;
        continue;
    }

⇒ **缓冲按下被当成"用户已松手"丢掉 → 激活后每一次鼠标移动又被 AdoptHeldButtonIfAny
   里同一个查询挡回去 → 拖动永远建立不起来**；而外框由 ShowHoverFrame 照常画出。
   这就是用户看到的「外框被样式包围，但鼠标怎么动窗口都移动不了」。

为什么"按住左键过一会儿再移动"就正常：那种时序里左键是在**激活之后**才按下的，
走的是一条完全不同的分支（`HandleMouseCore` 的 down 分支直接 `HandleButtonDown`），
根本不经过这道被污染的关卡。


------------------------------------------------------------------------
四、修复思路：判据只用「钩子事件账本」
------------------------------------------------------------------------
低级鼠标钩子能**直接看到**每一次鼠标键按下/抬起。账本语义精确且自洽：
    收到按下 + 尚未收到配对的抬起  ⟺  键还按着
抬起分支（OnMouseCore 的 up 分支）会把三本账全部清零，所以账本不会长期失真。
GetAsyncKeyState 在本进程被实测证明会漏报，拿它做判据只会把好账当坏账。

改动（work/fixed/HoldDrag.cs，累计补丁 50 hunk）：

 ① AdoptBufferedButtonsNow（激活瞬间）：删掉 `if (!IsButtonPhysicallyDown(i)) { 清账; continue; }`
    这道关卡。缓冲账里有按下就直接收养。
 ② AdoptHeldButtonIfAny（激活后随光标移动接管）：判据从"物理键状态 + 三本账"改成**只看三本账**
    （`_bufferedDown || _heldDuringHold || _passedDown` 任一为真即接管）。
    自有窗口可交互控件上的让路逻辑（拖滑块/选文本/点按钮）原样保留。
 ③ FlushBufferedClicks（触发键短按补还点击）：keepDown 也改成按账本判定（账本还在 ⟺ 用户仍按住），
    补"按下"而不补"抬起"，用户真实抬起稍后原样送达 —— 按住过程不再被打断。
 ④ 兜底：OnTriggerDeactivated 里若仍在拖动，立刻 _drag.End()（松开触发键一定收手；
    「鼠标抬起」这条同样可能落在钩子重装的缝隙里丢掉）。
 ⑤ 诊断留痕（长期保留，只在触发键按住/激活期间写，量极小）：
    · `[诊断] 鼠标键按下/抬起 键=… 触发[按住=… 激活=…] 缓冲=… 阈值期按住=… 已放行=… 拖动中=… 坐标=…`
    · `[诊断] 激活瞬间清点缓冲 …`（"物理按下"一栏仅作对照留痕，已不参与任何判定）
    · `FindTarget 没找到目标` 改为**无条件**记录（以前只在 quiet=false 时打，
      导致"激活瞬间补起"这条路径静默失败时日志一片空白）

------------------------------------------------------------------------
六、验证过程里的两个插曲（如实记录，避免下次重踩）
------------------------------------------------------------------------
1. 前几次 E2E 得出"仍然 +0,+0"，是因为**桌面上的管理员旧实例还活着**：
   本程序有单实例互斥（Mutex "Local\HoldDrag.SingleInstance.v1"，只对
   --selftest / --windowhost 等分支放行），新起的测试进程会**启动即退出**
   （子进程日志：「已有实例在运行，通知它把设置窗口显示出来」），
   而旧实例排在钩子链更前面、会先吞掉 Enter 的按下 —— 那几次量到的全是旧实例的行为。
   ⇒ **真实链路验收前必须先让旧实例退出。**
2. 中途按"物理键状态"方向改的第一版仍然 +0,+0：方向对了，但判据还得靠那个会漏报的查询，
   等于换了个地方踩同一个坑。抓到 `物理按下[False,False,False]` 这行现场日志后才改成账本判据。


------------------------------------------------------------------------
七、一个需要用户确认的边界（tap 那一档）
------------------------------------------------------------------------
若用户的实际习惯是「点一下左键就松开、然后再移动鼠标」，按当前"按住才拖"的语义不会拖动 ——
松开左键之后没有任何东西"按着"这个窗口。这属于产品语义选择：
    「按住才拖」  vs  「点一下抓住 / 再点一下放下」
用户原话里是「按住左键过一段时间再移动是能顺利移动的」，听起来是"按住"的习惯，
故本轮按"按住才拖"实现；若其习惯其实是"点一下抓住"，需另加粘滞模式。
